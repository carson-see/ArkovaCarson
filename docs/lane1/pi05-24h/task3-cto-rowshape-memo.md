# CTO Row-Shape Memo — direct-anchor proof materializer (SCRUM-2916/2917)

**From:** Lane 1 (Trust & Chain, DBA persona) · **To:** CTO (via RTE) · **Ruling due:** Jul 24 EOD
**Status:** DRAFT for ruling. No migration files authored (W3). Grounded in read-only prod census (Task 2) + code/schema read.

## 1. The decision in one sentence
The materializer must INSERT one `anchor_proofs` row for each SECURED anchor that classifies **`direct_anchored`** and currently has **no proof row** — an estimated **≈2.98M** (Task 2 census: 6,110 already-complete rows exist; ~99.8% of the ≈3.0M catalogue has none). This memo asks the CTO to rule on the **exact column payload of a direct-anchor proof row**, its **idempotency key**, **resume semantics**, and **rollback** — and the one hard coupling: the **0340 "SECURED ⇒ proof complete" trigger** predicate.

> **⚠ Count is a PROVISIONAL UPPER BOUND (DBA review HIGH-1).** The ≈2.98M is `total_SECURED − already_complete − ambiguous` with **`ambiguous` uncomputed** (Task 2 could not run the tx-cardinality probe read-only). It therefore also contains any `secured_without_tx` and shared-tx batch members lacking proof rows. **The materializer's insert authority is NOT "every anchor lacking a proof row" — it is a per-anchor `classifyAnchor(anchor, proof, txCardinality)` at insert time, inserting ONLY when `cls === 'direct_anchored'`.** The `receipt_id NOT NULL` constraint is a backstop (a null-tx `ambiguous` row would fail the INSERT), but ambiguous rows must be excluded up front, never minted as `direct_anchored`. Get the true direct-vs-ambiguous split from the census's own cardinality-probing path on an isolated mirror (or a `psql` aggregate) before quoting a final count. Per the performance review, that cardinality probe (~2.98M single-tx probes, no memo reuse for direct anchors) is the run's bottleneck (~1–3h), which is inherent, not a missing index.

## 2. Schema facts (fixed constraints the ruling must live within)
- `anchor_proofs` PK `id uuid`; **`anchor_id uuid NOT NULL`**; **`receipt_id text NOT NULL`** (no FK, no default); `merkle_root text NULL`, `proof_path jsonb NULL`, `batch_id text NULL`; 0340 columns `block_height`, `block_timestamp`, `block_hash text`, `block_header bytea`, `op_return_payload bytea`, `merkle_index int`, `proof_schema_version smallint NOT NULL DEFAULT 1`; 0354 column `proof_completeness_class text NULL`.
- **UNIQUE(`anchor_id`)** = `anchor_proofs_anchor_unique` → **the natural idempotency key** (one proof row per anchor).
- **0340 trigger** `enforce_secured_anchor_proof_complete` (GATED by GUC `arkova.proof_enforce_secured_complete`, currently **OFF**): when ON, it requires a proof row with `merkle_root` AND `proof_path` both populated. Direct anchors have **no merkle tree** — the classifier and §1.6 honesty rules **forbid fabricating one**.
  - **Corrected exposure (DBA review HIGH-2):** the trigger fires `BEFORE INSERT OR UPDATE OF status` and **short-circuits when `OLD.status = 'SECURED'`** (0340 body). So the ~2.98M already-SECURED back-catalogue rows are **NOT** re-litigated on a status touch that keeps them SECURED — the earlier "would reject the entire back catalogue on any status touch" framing was **wrong**. The real exposure is **FORWARD**: new direct anchors (HakiChain-style) making a genuine non-SECURED→SECURED transition would be rejected once the GUC is on. That is the case the 0359 predicate change must serve.

## 3. Recommended row shape (direct_anchored)
Per materialized direct anchor, INSERT:

| column | value | note |
|---|---|---|
| `anchor_id` | anchor.id | idempotency key |
| `receipt_id` | **anchor.chain_tx_id** | **RULING NEEDED (§5-A):** for a direct anchor the tx *is* the network receipt; no pre-existing receipt_id exists to reuse |
| `op_return_payload` | `ARKV`(4B)+fingerprint(32B)+suffix(8B) | reconstructable from the anchor row **without a chain call** (verified against Task-1 on-chain sample) |
| `block_height` | anchor.chain_block_height | already on the anchor row |
| `block_timestamp` | anchor.chain_timestamp | already on the anchor row |
| `block_hash` | anchor.chain_block_hash **or NULL** | **RULING NEEDED (§5-B):** only ~partially populated on anchors; full population is a **chain call** owned by `backfillProofCompleteness.ts` (SCRUM-2491), not this job |
| `block_header` | NULL (deferred to 2491) | bytea; needs a chain fetch |
| `merkle_root` | **NULL** | honest: direct anchors have no tree — never fabricate |
| `proof_path` | **NULL** | honest empty; do NOT write `[]` (that would read as already_complete under 0340) |
| `batch_id` | NULL | not a batch |
| `proof_completeness_class` | `'direct_anchored'` | 0354 label = the honest completeness signal |
| `proof_schema_version` | 1 | current |

**Rationale:** the row carries the *real* on-chain binding (tx + OP_RETURN commitment of the fingerprint) — which is exactly what a stranger uses to verify (Task-1 method) — while leaving merkle fields honestly NULL. Completeness is asserted via the **class label**, not a fabricated tree.

## 4. Idempotency, resume, rollback
- **Idempotency key:** `INSERT … ON CONFLICT (anchor_id) DO NOTHING` (or `DO UPDATE SET proof_completeness_class=EXCLUDED.…` if re-labeling is desired). Guarantees exactly one row/anchor; safe to re-run. Do **not** key on `id` (server default) — that defeats idempotency.
- **Resume:** mirror the classifier's proven pattern — durable `job_queue` checkpoint row (`type='...:materialize:checkpoint'`, terminal status `completed`), monotonic **cursor = last anchor_id ascending**, bounded pages (batchSize clamp 50–2000, maxBatches clamp per invocation). Worker restart resumes from cursor, never from zero. Re-classify each page fresh at insert time and **HALT before writing any page that turns `ambiguous`** (reuse the classifier's halt-on-ambiguous gate). **Progress MUST be derived from the cursor, never from a repeated bare `count=estimated` on `status=SECURED`** — the performance review measured that count at 13s→22s→timeout (unstable), while a cursor-bounded page is ~0.15s.
- **Rollback (corrected, DBA review MED-1):** do **NOT** overload `batch_id` as a run sentinel — `batch_id` has a partial index `idx_anchor_proofs_batch_id WHERE batch_id IS NOT NULL` (2.98M sentinels = 2.98M spurious index entries + ~3M fake "batches" polluting the SCRUM-2471 branch-backfill), and it contradicts the §3 row shape (`batch_id = NULL`). And do **NOT** scope rollback by `proof_completeness_class='direct_anchored'` alone — the classifier's UPDATE path writes that *same* label onto pre-existing rows, so a class-only DELETE could catch rows the materializer never inserted. **Use a run marker:** cleanest is a dedicated nullable `materialize_run_id uuid` column (its own tiny migration); acceptable fallback is `created_at ≥ run_start AND merkle_root IS NULL AND proof_path IS NULL AND proof_completeness_class='direct_anchored'`. Either way the 6,110 existing `already_complete` rows are safe (they predate the run and carry non-null merkle data). A backup + restore drill (SCRUM-2983) is the hard pre-execute gate regardless.

## 5. Open rulings the CTO must make
- **5-A `receipt_id` provenance:** confirm `receipt_id := chain_tx_id` for materialized direct rows (the honest "network receipt" for a direct anchor). Alternative: mint a synthetic `direct:<anchor_id>` — rejected here as less meaningful.
- **5-B chain-data columns now or later:** materialize the MINIMAL row now (no chain call: receipt_id, op_return_payload, height, timestamp, class) and let `backfillProofCompleteness` (SCRUM-2491) fill `block_hash`/`block_header` later — **vs** one insert-with-chain-data pass. Recommend **minimal-now + 2491-later** to keep the 2.98M pass chain-call-free and fast.
- **5-C 0340 trigger predicate (COUPLED MIGRATION) — SAFE FORM (DBA review HIGH-2):** the predicate change must serve **forward direct anchors** (not the already-SECURED bulk, which the trigger short-circuits). Do **NOT** trust the bare text label: `proof_completeness_class` is a service_role-writable `text` column CHECK-bounded to 4 values, so `... OR proof_completeness_class IN ('direct_anchored','already_complete')` lets any writer of that column forge SECURED-eligibility with zero real proof data (a §1.4 regression), and `'already_complete'` in the OR is redundant + dangerous (the classifier never even writes that label; `buildClassWriteSet` returns null for it). **Safe predicate:** `(merkle_root IS NOT NULL AND proof_path IS NOT NULL) OR (proof_completeness_class = 'direct_anchored' AND op_return_payload IS NOT NULL)` — i.e. the direct branch requires the **real on-chain binding** (`op_return_payload`), not just a label. This is a **separate migration** in the 0359+ train (Task 7), gated on this ruling and paired with a trigger unit test that proves a bare-label row with NULL merkle fields is REJECTED. Until it lands, GUC stays OFF.
- **5-D `already_complete` semantics for direct:** confirm direct rows count as "servable complete" for KPI/proof-bundle purposes even though `proof_bundle` (two-layer) stays null (FE proof-gate "state 1b"). The Task-1 finding shows direct anchors are OP_RETURN-verifiable; the downloadable two-layer packet is genuinely N/A, not missing.

## 6. What this memo does NOT assert (§1.5)
Does not assert the exact `secured_without_tx` (ambiguous) count — Task-2 could not compute it read-only (no index on `chain_tx_id IS NULL`; a `chain_tx_id IS NULL` filter seq-scans ~3M rows and times out even at LIMIT 1, per the performance review — **never add that filter to any materializer scan**); if > 0 those rows must be excluded from materialization and routed to ambiguity resolution. Does not author any migration (W3). Does not decide the GUC flip. **Scope note (AI review F3):** the ≈2.98M `direct_anchored` bulk are **pre-connector** anchors (public-records + HakiChain-style direct anchors), not connector-sourced; connectors are flag-off in prod, and future connector anchors drain through `processBatchAnchors` → gain `merkle_root`+`proof_path` → land as `already_complete`, correctly outside this materializer's scope.
