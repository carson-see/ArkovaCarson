## 1. Purpose + claims-review framing

### 1.1 What this is

An internal, **platform-admin-only**, **read-only** dashboard that lets a Arkova operator answer one question at a glance: *"Is production currently behaving the way we believe it is?"* It does this by surfacing three signals where a silent divergence between intended and actual state has a direct money, trust, or launch-clock consequence:

1. **DOUBLE_BILLING_RISK** — are we charging without anchoring, or anchoring without charging? (money-safety, risk **R-9**)
2. **Fail-open flag state** — is any kill-switch OFF in the database but still serving because a Cloud Run env var re-opened it? (risk **R-5**)
3. **Key/secret expiry** — is any credential (CE trial API key, signing/treasury keys, HMAC secret) approaching expiry? (risk **R-1**, dashboard-surface level only; deep mechanism owned by the sibling KEY-EXPIRY design — see §3.3)

### 1.2 Claims-review framing (CLAUDE.md §1.5 — measured / asserted / NOT asserted)

This spec, and the dashboard it specifies, is bound by the claims-review discipline. Stated precisely:

| Dimension | Statement |
|---|---|
| **What it MEASURES** | Counts and ratios derived from existing rows and existing telemetry: `org_credit_deductions` rows vs `anchors` rows in a window; the divergence between `flagRegistry`/`switchboard_flags` resolved state and the Cloud Run env value; the rate of `chain_rpc_fallback` events; days-until-`expires_at` for keys/secrets. All are **observations of state already recorded by the system.** |
| **What it ASSERTS** | Only that "the dashboard's count/ratio at refresh time `T` reflects the rows/telemetry visible to the worker's `service_role` connection at `T`." Each panel shows its own `as-of` timestamp and the data source it read. |
| **What it explicitly does NOT assert** | (a) That a non-zero DOUBLE_BILLING_RISK count **is** a double-charge — it is a *reconciliation mismatch to investigate*, which may be an in-flight anchor inside the grace window, a refunded deduction, or a connector/public-record anchor with no credit path. (b) That the chain actually broadcast or settled a transaction — that is the verifier/proof slice owned by **Lane-1** (cited, never re-derived here). (c) That a flag's *intended* value is the env value or the DB value — it asserts only that they **diverge**; which one is correct is an operator decision (the dashboard links to the controls page, it does not auto-remediate). (d) Any USD/treasury figure beyond what the existing treasury endpoints already compute. (e) Nothing about an individual user, document, or fingerprint — signals are aggregate counts/states only (§1.6 / §6 PII rule). |

**Corollary (drives the whole design):** because the dashboard only *reads* and *reconciles* existing state, it adds **zero new collection paths**. This is a hard Lane-1 review constraint (§6) and the central implementability guarantee: every number on the dashboard traces to a file/table/RPC that already exists on `main` (or is an explicitly-flagged INCOMING surface).

### 1.3 Why "reconcile existing collection" and not "instrument"

The three signals are precisely the three "asserted-vs-running" dimensions that **Lane-1's S0-5.2 drift/parity gate** already needs to check (env⊕DB divergence; provider drift = 100% fallback; CSP/allowlist drift). Building the dashboard on the same already-collected telemetry means VIS-01 (the dashboard) and S0-5.2 (the CI gate) consume **one shared threshold definition** (§5) and never drift apart. The dashboard is the human-facing read of the same truth the gate enforces in CI.

### 2.1 Signal 1 — DOUBLE_BILLING_RISK (money-safety, retires risk **R-9**)

#### Definition
A reconciliation count of money-path mismatches across three sub-signals:

- **1a. Charge-without-anchor** — an org-credit deduction was recorded but no corresponding anchor exists (or the anchor failed and the credit was never refunded).
- **1b. Anchor-without-charge** — an anchor was created for a billable path but no deduction (and no covering subscription/x402/admin/beta source) is recorded.
- **1c. Duplicate broadcast / double fee-spend** — the same transaction was broadcast more than once (a real double *fee* spend, distinct from the benign "already in mempool" no-op).

#### Risk retired
**R-9 (money-safety).** A silent charge-without-anchor is direct revenue-for-nothing (trust + refund liability); a silent anchor-without-charge is revenue leakage. The **DOUBLE_BILLING_RISK alarm built on this signal is the gate that Instant-Secure GA (VIS-01 S3) depends on** — Instant Secure cannot flip on until this alarm is wired and quiet (ceremonies §1.3 deliverable L2-D; this is the cross-lane dependency that makes Signal 1 the flagship).

> **Important join nuance (DBA review item — §6):** `org_credit_deductions.reference_id` is **not** a foreign key to `anchors.id`. Per migration `0326`, the FAST_TRACK_ANCHOR path uses `organization_rule_executions.id` as the `reference_id`. So 1a cannot be a naive `deductions LEFT JOIN anchors ON reference_id = anchors.id`. The reconciliation must resolve the reference chain (rule-execution → anchor) or compare counts within a window by `org_id`. The Sprint-1 team must pin the exact join in a `SECURITY DEFINER` RPC (see metric sketch) and the DBA must confirm the reference resolution. This nuance is *the* reason this is a spec, not a one-liner.

#### Metric definitions (precise + query sketch)

All three are computed by **one new read-only `SECURITY DEFINER SET search_path = public` RPC** (e.g. `get_double_billing_risk_counts(p_window_minutes int, p_grace_minutes int)`) that returns a small JSON of counts — same pattern as the existing `get_anchor_status_counts_fast` used by `admin-stats.ts:65`. No table writes; aggregation only; runs against the 1.4M-row `anchors` table via index, exactly like the existing admin RPCs.

- **M1a `charge_without_anchor_24h`** — *count of `org_credit_deductions` rows in the last `window` (default 24h) whose resolved anchor reference has **no** `anchors` row in `SECURED`/`SUBMITTED`/`BROADCASTING` within `grace` minutes (default 30) AND no matching refund (row still present ⇒ not refunded).* Sketch:
  ```sql
  -- inside get_double_billing_risk_counts (SECURITY DEFINER)
  SELECT count(*) FROM org_credit_deductions d
  WHERE d.created_at >= now() - make_interval(mins => p_window_minutes)
    AND NOT EXISTS (
      SELECT 1 FROM anchors a
      WHERE a.org_id = d.org_id
        AND a.created_at BETWEEN d.created_at - make_interval(mins => p_grace_minutes)
                              AND d.created_at + make_interval(mins => p_grace_minutes)
        AND a.status IN ('SECURED','SUBMITTED','BROADCASTING')
        AND a.deleted_at IS NULL
        -- DBA to confirm: tighten via resolved reference (rule_execution → anchor) once join is pinned
    );
  ```
  (The window/grace approach is the conservative interim until the `reference_id` chain is pinned; the pinned-join version is the Sprint-1 target — see §7.)

- **M1b `anchor_without_charge_24h`** — *count of `anchors` rows created in the last `window` with `deleted_at IS NULL`, a billable `status` (not `REVOKED`), `payment_source_type` that is **credit-billable** (i.e. NOT in `admin_bypass`/`beta_unlimited`/`stripe`/`x402`, OR null), and **no** `org_credit_deductions` row resolvable for that anchor.* Excludes connector/public-record anchors that have their own (non-credit) path. Sketch mirrors M1a with the existence test inverted and the `payment_source_type` exclusion applied.

- **M1c `duplicate_broadcast_24h`** — *count of distinct `anchors.chain_tx_id` values that received more than one genuine `sendrawtransaction` (a broadcast that was NOT classified by `isDuplicateTxError`) in the window.* This is **Lane-1-owned territory**: the count primitive is a broadcast-attempt telemetry that Lane-1 must confirm is observable (candidate: a structured log/Sentry event analogous to `emitRpcFallback`, or a broadcast-attempt audit row). **Open handoff to Lane-1** (§6): confirm the exact source row/event for a *non-no-op* duplicate broadcast; until confirmed, M1c renders as "source pending Lane-1 confirmation" rather than a fabricated number.

#### Collection = reuse which existing mechanism
- 1a/1b: **reuse existing tables** (`org_credit_deductions`, `org_credits`, `anchors`) via a **new read-only aggregation RPC** following the *existing* `get_anchor_status_counts_fast` / `get_anchor_tx_stats` pattern (`admin-stats.ts`). No new collection — the rows already exist; we only add a *read* RPC.
- 1c: **reuse the existing chain telemetry shape** (`emitRpcFallback` field-locking precedent in `services/worker/src/utils/sentry.ts:375`); Lane-1 confirms the duplicate-broadcast event source. No new instrumentation authored by Lane 2.

#### Threshold(s) (shared with S0-5.2 — see §5)
- `charge_without_anchor_24h` and `duplicate_broadcast_24h`: **warn at ≥ 1, page at ≥ 1** after the `grace` window (any confirmed money-path mismatch is operator-actionable; R-9 is zero-tolerance). The grace window absorbs in-flight anchors so the count is *settled* mismatches only.
- `anchor_without_charge_24h`: **warn at ≥ 1**; page threshold tuned by Lane-1 + Carson (leakage is lower-urgency than over-charge). Default page at a small N to avoid noise from edge billing states.

#### Refresh cadence
Dashboard panel: on page load + manual refresh + a 60s auto-refresh (mirrors `SystemHealthPage.tsx` `AUTO_REFRESH_MS = 30_000`; use 60s for the heavier reconciliation RPC). The **alarm** evaluation (for paging) rides the existing 5-minute `cron /db-health` cadence (`services/worker/src/routes/cron.ts:1498`, `runDbHealthMonitor`) — see §3.4.

### 2.2 Signal 2 — Fail-open flag state (retires risk **R-5**)

#### Definition
A divergence detector across the feature-flag system: for each kill-switchable flag, compare the **DB switchboard value** (`switchboard_flags.enabled`) against the **Cloud Run env value** (`process.env[FLAG]`). A flag that is **OFF in the DB but ON in env is a fail-open exposure** — because several runtime paths fall back to the env value on a transient DB read failure and would silently re-enable a killed feature. Plus a chain-specific fail-open: **`BITCOIN_UTXO_PROVIDER` fallback rate at 100%** means the sovereign RPC is functionally unused and we are fully dependent on the public `mempool.space` SPOF.

#### Risk retired
**R-5 (fail-open).** This is grounded in a real, documented SEV1 class:
- `services/worker/src/middleware/aiFeatureGate.ts` header (SCRUM-2247 / HARDEN-1-D, lines 14-32) documents the **fixed** request-gate: kill-switchable flags fail **CLOSED**, the env var is *not* a re-open path.
- BUT `services/worker/src/middleware/agents.md` (lines 30-43, "Sibling-consumer audit") states plainly that `flagRegistry.ts` `init()`/`refreshDbFlag()` **still** uses the env-var fallback on a DB error for all `DB_FLAGS` (including kill-switches like `MAINTENANCE_MODE`), "so the registry snapshot can be fail-OPEN on a startup DB blip" — flagged as an out-of-scope follow-up.
- Confirmed in code: `flagRegistry.ts` lines 112-117 and 131-137 do exactly this env fallback; contrast `grcFeatureGate.ts` lines 35-39 (env fallback on error) vs the hardened `aiFeatureGate.ts` `failDefault()` (lines 68-75, fail-closed).
- The same `agents.md` "Ops note (out of code scope)" (lines 41-43): *"prod env vars (`ENABLE_SEMANTIC_SEARCH`, `ENABLE_AI_FRAUD`, etc. ON in Cloud Run) and the `switchboard_flags` rows must be re-synced so the intended state is the DB row, not a divergent env fallback."* **This dashboard makes that divergence visible** instead of leaving it as a buried prose note. It is the literal "2026-05-30 finding" in Lane-1's inventory.

| Source | Path / symbol | Role |
|---|---|---|
| Env-side flag resolution | `services/worker/src/middleware/flagRegistry.ts` — `flagRegistry.getAllFlags()` returns `{ [flag]: { value, source: 'env' \| 'db' } }` (lines 182-188) | Already exposes the *resolved* value + whether it came from env or DB. The `source: 'env'` for a flag that *should* be DB-backed is itself the smell. |
| DB-side flag truth | table `public.switchboard_flags` (cols incl. `flag_key`, `enabled`) — read pattern at `aiFeatureGate.ts:110`, `grcFeatureGate.ts:30`, `adesFeatureGate.ts:50`, `flagRegistry.ts:108`; written by `src/pages/PlatformControlsPage.tsx` (`UPDATE switchboard_flags SET enabled = …`, line ~161) | Source of truth per SCRUM-2247. The flip UI writes here + to `switchboard_flag_history`. |

> **Scope of "in-scope flags":** Lane-1's inventory names the three the dashboard must surface: **`ENABLE_PROD_NETWORK_ANCHORING`**, **`ENABLE_AI_FRAUD`**, **`ENABLE_SEMANTIC_SEARCH`** (env⊕DB divergence) plus **`BITCOIN_UTXO_PROVIDER`** fallback rate. The dashboard SHOULD render the divergence for the full kill-switchable set (`ENABLE_AI_FRAUD`, `ENABLE_SEMANTIC_SEARCH`, `ENABLE_AI_REPORTS`, `ENABLE_VISUAL_FRAUD_DETECTION`, `MAINTENANCE_MODE`, `ENABLE_PROD_NETWORK_ANCHORING`) since the `flagRegistry` already tracks all of them; the named three are the minimum.

#### Metric definitions (precise + query sketch)

- **M2a `flag_env_db_divergence`** — *for each in-scope kill-switchable flag `F`: a divergence record `{ flag: F, db_enabled: bool|null, env_enabled: bool, diverged: bool }` where `diverged = (db_enabled IS NOT NULL) AND (env_enabled = true) AND (db_enabled = false)`.* The dashboard surface count is `count(diverged = true)`. The **fail-open** orientation (env-ON re-opening a DB-OFF kill-switch) is the one that pages; the inverse (env-OFF, DB-ON) is shown as an informational "drift" but is fail-*closed* so it is warn-only. Sketch (worker-side, in a new admin handler analogous to `admin-health.ts`):
  ```ts
  // Pseudocode — runs inside an isPlatformAdmin-gated /api/admin/flag-divergence handler
  const dbRows = await db.from('switchboard_flags').select('flag_key, enabled').in('flag_key', IN_SCOPE_FLAGS);
  const dbMap = new Map(dbRows.data?.map(r => [r.flag_key, r.enabled === true]));
  const divergence = IN_SCOPE_FLAGS.map(F => {
    const db_enabled = dbMap.has(F) ? dbMap.get(F)! : null;
    const env_enabled = process.env[F] === 'true';
    return { flag: F, db_enabled, env_enabled, fail_open: db_enabled === false && env_enabled === true };
  });
  ```
  (No new table; reads the same `switchboard_flags` rows the gates already read + the worker's own `process.env`.)

- **M2b `utxo_provider_fallback_rate`** — *the share of `listunspent` (and, as they adopt `emitRpcFallback`, `getrawtransaction`/`getblockheader`/fee-estimation) calls in the window that emitted `chain_rpc_fallback: true`, over total such calls.* `100%` ⇒ sovereign RPC functionally dead ⇒ full `mempool.space` SPOF dependency. **Reuses the existing `emitRpcFallback` event already feeding `db-health-monitor`** — the Sprint-1 work is to surface the already-collected rate, not to add a counter. (Denominator source — total `listunspent` attempts — is a **Lane-1 confirmation item**, §6: either a paired success breadcrumb or a call counter; until confirmed, render numerator-only "fallback events in window" with an explicit "rate denominator pending Lane-1" note.)

#### Collection = reuse which existing mechanism
- M2a: **reuse** `flagRegistry.getAllFlags()` (env/db source already tracked) + a direct `switchboard_flags` read (same query the gates run) + `process.env`. No new collection.
- M2b: **reuse** the `emitRpcFallback` telemetry that already exists and already "feeds the db-health-monitor view" by the file's own comment. No new collection.

#### Threshold(s) (shared with S0-5.2 — see §5)
- `flag_env_db_divergence` (fail-open orientation): **warn at ≥ 1, page at ≥ 1.** A kill-switch that is OFF in DB but ON in env is a live SEV1-class exposure (SCRUM-2247). This is the **same predicate** the S0-5.2 drift gate uses for "env⊕DB divergence."
- `utxo_provider_fallback_rate`: **warn at ≥ 90% sustained over 1h, page at 100% sustained over 1h.** Matches the call-site's stated intent ("alert if it stays at 100%", `utxo-provider.ts:476-477`) and the `db-health-monitor`'s "continuous > 1h" alerting style (`db-health-monitor.ts:8-9`).

#### Refresh cadence
M2a is cheap (one small select + env read) → 30s auto-refresh on the panel, like `SystemHealthPage`. M2b reads the rolling 1h fallback window → recompute on the 5-min `cron /db-health` cadence and cache for the panel.

## 3. Dashboard spec

### 3.1 Where it lives (and why)

**Proposal: a new platform-admin page `PlatformVisibilityPage` at route `ROUTES.ADMIN_VISIBILITY = '/admin/visibility'`, sibling to the existing admin pages**, rather than overloading `SystemHealthPage` or `PlatformOverviewPage`.

Justification:
- `SystemHealthPage.tsx` is *liveness* (is the worker up? Supabase latency? memory?). `PlatformOverviewPage.tsx` is *business volume* (users, orgs, records, subscriptions). Neither is *integrity/divergence*. The three signals are a distinct concern — "is prod **honest**" — and warrant their own page so the alarm semantics (warn/page) are not diluted by green-by-default health tiles.
- It reuses the **exact existing admin scaffolding**: `AppShell`, `Card`/`CardHeader`/`CardContent`, `Badge`, `Skeleton`, the `isPlatformAdmin(user?.email)` guard + "Unauthorized" view, and the `lazyWithRetry` + `AuthGuard` + `RouteGuard` route registration in `src/App.tsx` (lines 301-311). So it is *additive*, not a refactor — Sprint-1 cost is low.
- It links *to* `SystemHealthPage` (`/admin/health`) and `PlatformControlsPage` (`/admin/controls`) so an operator who sees a divergence can jump straight to the flip UI.

### 3.3 RBAC (platform-admin only — cite the gating pattern)

Identical to the existing admin pages — **no new auth primitive**:
- **Front-end:** route guarded by `AuthGuard` + `RouteGuard` (as `/admin/health` is, `src/App.tsx:302`); page body checks `isPlatformAdmin(user?.email)` from `src/lib/platform.ts` and renders the standard "Unauthorized" `AppShell` view for non-admins (copy mirrors `SystemHealthPage.tsx:96-113`).

### 3.4 No-PII + Sentry-scrubbing rules

- **Counts and states only, never rows.** No email, no document fingerprint, no `key_hash`, no raw secret value, no per-user identifier crosses the API boundary. Panels show aggregate counts, flag booleans, and days-to-expiry — nothing that identifies a person or document (CLAUDE.md §1.4/§1.6; ceremonies pre-mortem P6).
- **USD/treasury** figures stay platform-admin-gated and reuse only what the existing treasury endpoints already compute; the visibility board prefers *count* over *dollar* where a count answers the question.
- **Sentry scrubbing** applies to every alarm event the dashboard's collectors emit: route through the existing `Sentry` wrapper in `services/worker/src/utils/sentry.ts` (the same module that hosts `emitRpcFallback` and the `db-health-monitor` `emitSentry`), which the codebase already mandates scrub PII (CLAUDE.md §1.4 — "No Sentry events containing user emails, document fingerprints, or API keys"). Alarm payloads carry only flag names, counts, thresholds, and credential *labels* — never values.
- **Tags, not bodies:** follow the `db-health-monitor` precedent (`classifyAlert` / `extractContextTags`, `db-health-monitor.ts:155-186`) — Sentry events carry `alert_type` + bounded context tags, not raw data.

The dashboard is the *read*; the *paging* rides existing rails:
