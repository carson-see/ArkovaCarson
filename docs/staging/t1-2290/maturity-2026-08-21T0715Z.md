## Caveat 1 — the first 31 min of revision clock carried no load

The rig was first deployed with tag `t1-2290`. `scripts/staging/load-harness-env.ts:18-24`
accepts **only** `pr-<digits>` or `train-*`, so every cycle aborted immediately and the rig
saw nothing but five manual health probes between 04:41:33Z and ~05:12Z. Fixed by attaching
the correctly named `pr-2290` tag to the **same revision**
(`update-traffic --set-tags`), which left the clock untouched — verified `00003-qiz` @
`04:41:33.519799Z` before and after.

The liveness gate caught this in real time (`cycle done rc=1` →
`SOAK IS NOT PRODUCING VALID EVIDENCE`). The loaded window in this document therefore
starts at 05:12Z, not at the clock start.

## Caveat 2 — `/api/v1` was dark for the entire window

The rig's `switchboard_flags` table does not contain `ENABLE_VERIFICATION_API`, so
`get_flag` fails closed and `/api/v1/*` returned a sub-10 ms 503 before reaching
application code. **No flag was written to the rig** — mutating a rig mid-soak would taint
its own evidence.

For this PR that is acceptable and is stated rather than glossed: #2290 changes only the
worker's dependency tree (`@aws-sdk/client-kms` 3.1106.0→3.1111.0, `@peculiar/asn1-*`
2.8.0→2.9.0, `@sentry/node`, `@supabase/supabase-js`), which is exercised by worker startup,
the `database`/`anchoring`/`kms` health checks, and 12,033 requests through the auth,
rate-limiting and cron paths. `kms: ok` is the most direct signal — `@aws-sdk/client-kms` is
one of the bumped packages.

It would **not** be acceptable for a PR that changes `/api/v1` behaviour. See
`../wave2-2026-08/maturity-2026-08-21T0351Z.md`, where the same darkness left #2211 and
#2233 uncovered.
