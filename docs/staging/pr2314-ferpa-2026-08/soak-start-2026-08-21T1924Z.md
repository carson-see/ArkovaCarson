### DISCLOSED DEVIATION — how the schema got onto this rig

The operator constraint for this session was **no `supabase db push --linked`**. The rig's
schema was therefore replayed file-by-file through the Supabase **Management API**
(`POST /v1/projects/{ref}/database/query`), each file sent verbatim with its md5 logged,
and each recorded in `supabase_migrations.schema_migrations` with the numeric prefix as
`version` and the remainder as `name` — the same shape `db push` produces. 111 files,
ledger head `0409`, matching `origin/main` and the other rigs exactly, before `0415`.

Two honest caveats on that replay:

1. **One file was NOT applied byte-exact.**
   `0381_docusign_envelope_metadata_lookup_indexes.sql` uses `CREATE INDEX CONCURRENTLY`,
   which cannot run inside the transaction the Management API wraps every request in
   (`25001`). ` CONCURRENTLY` was stripped for that one file and the fact was logged. On a
   greenfield rig the resulting index is identical — `CONCURRENTLY` changes the locking
   strategy while building, not the object. The other 110 files, including `0415`, went in
   verbatim.
2. **Ledger rows were inserted by this replay.** That is a migration-ledger write. It is
   disclosed here rather than buried: it is provisioning a brand-new isolated project to a
   known head, not repairing or laundering a shared rig, and no `migration repair`, no
   `db push --linked`, and no destructive operation on shared staging was run. Nothing
   was written to any other rig.

## Load driver
