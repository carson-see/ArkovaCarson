# CTO Design Brief — DocuSign Bilateral Coverage + Record Deep Links
Date: 2026-08-29. Author: CTO session. Status: DRAFT for pre-mortem debate.

## Problem statements (from founder)
- **F1**: Integration only captures envelopes the connected org SENDS. Envelopes the org RECEIVES/SIGNS that originate from another organization's DocuSign account are never ingested.
- **F2**: On the record detail page's METADATA section: `account id` value becomes a hyperlink to the DocuSign account (no naming), `envelope id` value links to the signed document on DocuSign, and NEW `signer id` row(s) link back to each signer's account.

## Verified ground truth (do not re-litigate; citations exist in discovery reports)
- Ingestion today: account-level DocuSign Connect (`allUsers:true`, events `['envelope-completed']`, deliveryMode SIM) + daily/hourly account-scoped reconcile polls. All keyed on the OAuth-connected `accountId`. Sender-only is structural.
- No recipient/signer identity is captured anywhere (strict Zod schema `DocusignEnvelopeCompleted` has no recipients field; only notary detection touches `recipients.signers[]` transiently).
- Metadata writers: `jobs/docusign-envelope-completed.ts` p_metadata -> `connector_artifact.metadata` -> spread into `anchors.metadata` by `jobs/connector-artifact-drain.ts` (+ `connector_source`, `connector_artifact_id`, `external_ref`).
- UI: authed `/records/:id` -> `AssetDetailView.tsx:742-760` renders `Object.entries(visibleMetadata)` with `key.replace(/_/g,' ')`; hides keys in `ANCHOR_CREDENTIAL_METADATA_HIDDEN_KEYS`, keys starting `_`, fraud keys. Public `/verify/:publicId` uses RPC `get_public_anchor` -> SQL `sanitize_metadata_for_public` (strips PII denylist + ALL top-level `_`-prefixed keys) -> client `PUBLIC_METADATA_HIDDEN_KEYS` + `CredentialRenderer` `METADATA_DISPLAY_HIDDEN_KEYS`. All filters are DENYlists — new keys auto-render on BOTH surfaces unless `_`-prefixed or explicitly hidden.
- Prod: exactly 21 DocuSign anchors (all connector-path; declared-hash `source_envelope_id` path has 0 rows), 1 active org integration, base_uri `https://na4.docusign.net` (prod env). `DOCUSIGN_DEMO=false` since PR #1668.
- DocuSign facts: (a) account-level Connect NEVER fires for foreign-account envelopes; (b) **Recipient Connect** is the sanctioned webhook for org-user-as-recipient, any sending account, includes `envelope-completed`, same payload shape, configured in the CUSTOMER's DocuSign Admin console (no API provisioning field found), prerequisites: DocuSign Organization + claimed email domain + Access Management with SSO (plan-gated); (c) cross-account recipient-token API fetch is unreliable and being LOCKED DOWN by DocuSign's 26.3 release (Demo 2026-09-12, Prod 2026-09-21 — requires userId AND accountId on GetEnvelope/GetRecipient/GetDocument); (d) polling (`user_filter=recipient`, `folder_ids=inbox`) only reaches the connected account's own store; DocuSign anti-polling policy: >=15 min per object, app-approval-gating; (e) deep links verified live 2026-08-29: `https://apps.docusign.com/send/documents/details/{envelopeId}` (200), demo `https://apps-d.docusign.com/...` (200), `https://apps.docusign.com/send/home?account={accountId}` (preserves param); `admin.docusign.com/users/{userId}` DROPS the GUID (dead); no public per-user/account resolution URL exists; (f) recipient schema fields available: `name, email, recipientId, recipientIdGuid, userId, status, signedDateTime, deliveryMethod, routingOrder, recipientAuthenticationStatus{...}`; Connect and Recipient Connect deliver the same event payloads.

## Proposed architecture

### F1 — Inbound envelope ingestion via Recipient Connect
1. **Mechanism**: customer-side Recipient Connect configuration ("Custom Recipient") pointed at our existing `/webhooks/docusign` endpoint with `?customrecipient=true` marker. Events: `envelope-completed` (MVP). We publish a setup runbook + in-product qualification/setup guide; we CANNOT auto-provision it (console-only).
2. **Classification**: webhook handler classifies `direction: 'inbound'` via the `customrecipient` query marker AND payload heuristics (envelope's sender account != any connected account for the resolved org). Outbound path unchanged (`direction: 'outbound'` added for new records; absent = legacy outbound).
3. **Attribution**: resolve org by the payload `accountId` (Recipient Connect config lives under the customer's account umbrella, so the notifying account should be the customer's). Defense: if `accountId` resolves to no integration -> existing orphaned-drop. HMAC: verified against the org's `hmac_keys` array (customer pastes the same HMAC key from their Recipient Connect config into Arkova, or we reuse the account-level key when DocuSign scopes HMAC per-account — implementation must verify which; treat as open question OQ-1).
4. **Document acquisition (no cross-account API fetch, ever)**: prefer in-payload document bytes when the customer's Recipient Connect config has include-documents enabled -> SHA-256 in memory -> discard (per CLAUDE.md section 1.6A). Else fall back to DocuSign-declared per-document `sha256` from the SIM payload -> anchor with `fingerprint_provenance: 'declared'` metadata. Never call `/envelopes/{id}/documents/*` for inbound envelopes (cross-account; being locked down Sept 2026).
5. **Data model**: NO new tables/columns. `connector_artifact` reused with `metadata.direction='inbound'`, `metadata.sending_account_id=<foreign GUID>`; dedupe key stays `(org_id, source, external_ref, revision)`. `organization_rule_events.payload` carries the extras (<=16KB cap — signers bounded at 20 entries).
6. **Fallback for non-qualified customers**: existing client-side upload path (section 1.6). The "CC our connected account" idea is DEAD (recipient status does not fire account-level Connect — contradicts verified fact (a)). DocuSign "Forward" of a completed envelope creates a NEW envelope owned by the forwarder (works via existing path, documented as manual stopgap only).
7. **Flags**: new `ENABLE_DOCUSIGN_INBOUND` (default false), independent kill-switch semantics like existing connector flags.

### F2 — Metadata deep links + signer rows (authed record page only, this iteration)
1. **Signer capture (worker)**: extend `DocusignEnvelopeCompleted` Zod schema with OPTIONAL minimal recipients parse; persist ONLY pseudonymous GUIDs + status/timestamp: `_signers: [{recipient_id_guid, user_id?, status, signed_at?}]` (cap 20), plus `_docusign_env: 'prod'|'demo'` (from integration base_uri/DOCUSIGN_DEMO at event time). NO name/email persisted anywhere (CTO ruling: recipient PII gets section-1.6A document-byte discipline — GUIDs only). `_` prefix means SQL public sanitizer auto-strips; authed UI generic dump auto-skips; public client filters are redundant cover.
2. **Link rendering (frontend)**: new `src/lib/docusignLinks.ts` — strict UUID/GUID validation before URL construction onto FIXED https bases (no metadata value ever becomes an href without GUID validation; immune to `javascript:`/URL injection by construction). When `connector_source==='docusign'`:
   - `account id` row value -> `<a href="https://apps.docusign.com/send/home?account={accountId}">` (env-switched base).
   - `envelope id` row value -> `<a href="https://apps.docusign.com/send/documents/details/{envelopeId}">`.
   - NEW `signer id` rows (one per `_signers` entry, rendered in the same metadata block style from the hidden key): display GUID (prefer `user_id` when present — the signer's DocuSign account id — else `recipient_id_guid`), link -> the envelope details URL (DocuSign's only signer-verification surface; per-user profile URLs verified nonexistent). Tooltip copy explains "Opens the signing record in DocuSign".
   - All links: `target="_blank" rel="noopener noreferrer"` + `ExternalLink` icon, style per `CtdlDataLink` precedent; copy strings in `src/lib/copy.ts` ("DocuSign" and "signer" are lint-clean; verify "envelope" against `lint:copy` — banned list does not include it).
3. **Legacy records** (21 in prod): account/envelope links render from existing metadata (default env=prod). No signer rows (no data). Optional follow-up story: reconciliation-time enrichment of `_signers` for OWN-account envelopes only (never cross-account).
4. **Public page**: NOT linkified this iteration (explicit follow-up decision; public behavior change deserves its own review). Signer GUIDs never reach public surfaces (SQL strips `_*`).

## Open questions for red-team
- OQ-1: HMAC key scoping for Recipient Connect configs (same account key? separate per-config key?) — affects onboarding UX + verification code.
- OQ-2: Does Recipient Connect SIM payload include `envelopeDocuments[].sha256` and/or document bytes identically to account Connect? (Research says "same payloads"; must be verified against a live/demo config during implementation; PR-C ships behind flag regardless.)
- OQ-3: Payload `accountId` semantics for Recipient Connect (customer's vs sender's account) — attribution correctness hinges on it; handler must tolerate both without security holes.
- OQ-4: `queue_scope` for inbound: org queue always (MVP) vs member routing by recipient user — MVP = org queue; member routing follow-up.
- OQ-5: Fingerprint re-derivability semantics for inbound declared-sha256 anchors (SCRUM-3253 caveat surface) — proof copy must state what is measured vs asserted (section 1.5 / R-7).
