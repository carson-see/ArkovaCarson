## Why window 1 was voided

Window 1's preflight returned `environment_type = fixture_seeded`, exit 1, failing exactly
one check: `submitted_anchors` — *"Zero SUBMITTED anchors."* For a PR whose entire surface is
anchor-lifecycle job code, that is the check that matters: the rig had nothing for the code
under test to operate on. §1.11A forbids starting or claiming a soak on a project whose
preflight fails, so the window was abandoned at ~1.65 h rather than run to 48 h and produce
evidence that could not be cited.

### The reclaim mechanism — corrected

Window 1's stand-up concluded that the soak's own `2249-anchor-expiry-sweep` probe had
reverted the fixture anchor, and therefore that "this window can never reach a passing
preflight while its driver runs." **That attribution is wrong**, and it pointed at a fix that
would not have worked.

`jobs/anchorExpirySweep.ts` selects **only**:

```ts
.eq('status', 'SECURED').is('deleted_at', null)
.not('expires_at', 'is', null).lt('expires_at', nowIso)
```

and transitions those rows to `EXPIRED`. It has no path that reads or writes a `SUBMITTED`
row. Stopping or retargeting the probe would have changed nothing.

The actual reclaimer is `public.recover_stuck_broadcasts()`, rewritten by
`supabase/migrations/0379_f3_recover_submitted_null_txid.sql`:

```sql
WHERE a2.status IN ('BROADCASTING', 'SUBMITTED')
  AND a2.updated_at < now() - (p_stale_minutes || ' minutes')::interval   -- default 5
  AND a2.deleted_at IS NULL
  AND a2.chain_tx_id IS NULL
  AND NOT EXISTS (... anchor_txid_journal PENDING/HELD ...)
```

driven by the in-process `recover-stuck-broadcasts` cron (`routes/scheduled.ts`,
`*/2 * * * *`, active in all environments). `scripts/staging/seed-baseline-fixture.sql`
inserts its SUBMITTED anchor with `chain_tx_id` NULL — precisely that predicate.

**The row names its own reclaimer.** Read directly at 2026-08-21T20:14Z:

```

status     PENDING
updated_at 2026-08-21 19:00:19.155804+00
metadata   { "_recovery_reason": "stuck_submitted_null_txid",
             "_recovered_from_status": "SUBMITTED", ... }
```

`stuck_submitted_null_txid` appears in exactly one place in the codebase: the SUBMITTED
branch `0379` added. This is systemic, not rig-specific — **every** isolated rig seeded with
`seed-baseline-fixture.sql` loses its fixture ~7 minutes after provisioning. Filed as
[`FD-SEED-1`](../findings/FD-SEED-1-baseline-fixture-self-reverts-in-7-minutes.md); the seed
file itself is a `.sql` change and needs a PR, so it is **not yet fixed upstream**.

A parallel session filed [`FD-TRAIN6-1`](../findings/FD-TRAIN6-1-soak-driver-invalidates-its-own-preflight.md)
(SCRUM-3189) on the same symptom while this work was in flight. Its general rule — *check whether
the driver's own actions can violate the preconditions its window is judged against* — is right and
worth keeping. Its named mechanism is not, and a correction banner now says so at the top of that
file. The distinction is not pedantic: its step 4 ("re-point the driver's sweep probe at the

### Set A — 5 durable SUBMITTED anchors (`5eed0002-0000-0000-0000-00000000000{1..5}`)

`status='SUBMITTED'`, `chain_tx_id` = a distinct synthetic 64-hex value (not a real
transaction), `legal_hold = true`. Every live mutator on this rig excludes them, and the two
exclusions are independent because two different jobs mutate SUBMITTED rows:

| Mutator | Cadence | Predicate that excludes Set A |
|---|---|---|
| `recover_stuck_broadcasts()` (0379) | `*/2` in-process | `chain_tx_id IS NULL` — ours is NOT NULL |
| `autoConfirmMockAnchors()` (rig has `USE_MOCKS=true`) | `*/2` in-process | `legal_hold = false` — ours is true |
| `monitorStuckTransactions()` | `*/10` | `useMocks` early-return **and** `legal_hold = false` |
| `rebroadcastDroppedTransactions()` | `0 */6` | `useMocks` early-return **and** `legal_hold = false` |
| `detectReorgs()` | `*/10` | `useMocks` early-return **and** `legal_hold = false` (and SECURED-only) |
| `populate-confirmation-proofs` | `*/15` | not scheduled — `ENABLE_CONFIRMATION_PROOF_BACKFILL` unset |
| `processBatchAnchors()` | `*/10` | PENDING-only, and `MIN_BATCH_THRESHOLD` is 3,000 |

`legal_hold = true` alone is **not** sufficient: `0379` deliberately does not check
`legal_hold` (its header explains why — recovery-to-PENDING is not a delete/revoke/supersede).
That is exactly why the old one-anchor fixture died.

`chain_tx_id` NOT NULL is also the more correct shape on its own merits:
`machines/bitcoinAnchor.machine.ts` INV-1b (`submittedRequiresChainTx`) says a SUBMITTED
anchor with a null txid is unreachable through every modeled write path. The old seed was
manufacturing a state the state machine says cannot exist, and `0379` is the self-healing net
that cleans it up. Every other SUBMITTED→PENDING write site in the worker
(`batch-anchor.ts:1138/2307/2389`, `publicRecordAnchor.ts:355`) is gated on
`.eq('status','BROADCASTING')` and cannot reach a SUBMITTED row. There are **zero** `pg_cron`
jobs on this rig (`select count(*) from cron.job` → 0), so no DB-side scheduler exists either.

### Set B — 100 SECURED anchors that give the sweep real work (`5eed0003-…`)

`status='SECURED'`, synthetic `chain_tx_id`, `chain_block_height` 900001–900100,
`legal_hold = true`, `expires_at`:

* `k = 1..4` — already past at seed time, so the very first sweep pass had work;
* `k = 5..100` — `now() + (k-4)×30 min`, i.e. one anchor falling due **every 30 minutes**

Without this, `/jobs/anchor-expiry-sweep` returned `checked: 0` on every pass for the whole of

### Why Set B is also the poison row #2249 exists for

Window 1's own coverage table flagged *"the actual defect — a malformed row not DoS-ing the

## Load driver — what changed

`/Users/carson/arkova-soak/train6/train6-load-loop.sh` (window 1's copy kept as
`train6-load-loop.window1.sh.bak`), supervised back-to-back by
`/Users/carson/arkova-soak/train6/supervisor.sh` until the window closes.

Retained from window 1: startup token mint with hard-fail, no `--audiences`, per-probe
expected status **and** required JSON field, `401/403 = FAIL unless declared`.

Added:

1. **A dedicated `429` counter** (`requests.status_429`), separate from `status_other`. A 429
   on a probe that did not declare it is now a hard FAIL tagged `RATELIMIT:`, and `401`/`403`
   mismatches are tagged `AUTH:` so an auth regression can never read as generic noise.
2. **A rate budget enforced at startup, against 60 req/min — not §1.10's 100.**
   `apiIpShadowGuard` (`services/worker/src/index.ts:413`) is mounted on all of `/api` at
   `maxRequests: 60` and skips only `/api/v1` requests bearing an API key, so 60 is the real
   anonymous ceiling per egress IP, and every concurrent soak driver on this host shares that
   IP. The driver computes its worst-case offered rate
   (`60/CORE_INTERVAL + ceil(7×60/MEMBER_INTERVAL)` = **8 req/min** at the configured
   `CORE_INTERVAL=10`, `MEMBER_INTERVAL=300`) and refuses to start above 45. Both paths it
   actually uses are outside that bucket anyway — `/api/health` is registered at
   `index.ts:213`, *ahead* of the guard at `:418`, and `/jobs/*` is not under `/api` — but the
   check is enforced so a future probe added under `/api` cannot silently blow the ceiling.
3. **A fixture guard.** Every member pass re-measures
   `count(*) where status IN (SUBMITTED, SECURED, EXPIRED)` on the rig and writes it into the
   cycle's evidence file as `fixture.submitted` / `fixture.secured` / `fixture.expired`, with
   a hard floor of 5 SUBMITTED. Window 1's failure was invisible for eight minutes precisely
   because nothing watched this — a preflight is a point-in-time assertion and this turns it
