## Verdict, stated before the numbers

**The clock holds and the worker stayed healthy for 48 hours under continuous load. The window's
HTTP evidence is nonetheless weak, and it does not evidence that migrations 0410–0414 behave
correctly.** Three separate things have to be said plainly:

1. **`/api/v1` is DARK on this rig.** Its `switchboard_flags` carries no `ENABLE_VERIFICATION_API`

   volume against `/api/v1` measures anything on this rig.

   **60 req/min** anonymous ceiling ([[FD-LOAD-1]]). 85.6 % of pre-switch requests were `429`. The
   events, reads and webhook legs recorded `errorRate = 1` in **every** cycle.

   nothing more.** The acceptance instrument for five DB-level migrations is targeted SQL against
   the rig database, and that is supplied below. It is the substantive evidence in this record;
   the HTTP window is context.

**T3's own required trigger evidence is absent** — the rig holds exactly one anchor. See
"§1.12 requirements NOT met".

At 02:00Z on 2026-08-22, **four revisions of `arkova-worker-staging` each ran the GDPR retention
cron against `fizyjojbebyalirtjjht` within ten seconds** — `00300-few` (02:00:00Z), `00294-tev`

The mechanism: eight retired-but-not-deleted tagged revisions (`00283-puq` … `00294-tev`) still
carry warm instances running in-process `node-cron`. Instances that started before the
2026-08-19T19:53Z secret rotation hold the *deleted* project URL and fail with `ENOTFOUND`

condition was not met.** In this window the contamination is benign — every run was a no-op on an
almost-empty database — but the isolation property that makes shared-staging evidence trustworthy
