| Failure we want to prevent | Early sign | Control / response |
|---|---|---|
| Merge unexpectedly releases unsoaked code | Worker/edge pause missing; frontend main auto-publishes | Verify all deployment holds before merge; no manual override during the hold |
| Soak tests the old backend | UI preview looks new but /api reaches stable production | Record frontend, API and MCP routing plus observed backend identity before clock start |
| Staging credentials can affect production | Shared cron secret or privileged default service account remains | Complete AR20-32 cloud remediation and effective denial checks; do not accept source-only proof |
| Candidate unexpectedly runs production jobs | Warm no-traffic revision starts webhook, credit, cleanup or Drive timers | Inventory enabled timers and choose monitored shared-background behavior or reviewed candidate-only suppression; stop on behavior outside that approved mode |
| Notifications disappear after a successful action | Domain change commits but no delivery record exists | Close AR20-13 transaction-to-durable-delivery gap and test crash/retry boundaries |
| Duplicate charge, email or key operation | Repeated submission creates another side effect | Exercise idempotence and concurrency; preserve ambiguity instead of blindly resending |
| Public output leaks recipient data | Preview/proof/private metadata appears in public responses | Test signed-out output and altered identifiers; stop immediately on leakage |
| Green soak never exercises the feature | Flags off, zero events, wrong credentials or empty queues | Record real changed-behavior witnesses and counters; an idle healthy service is insufficient |
| Agent revocation audit persistence fails | Revocation transaction rolls back and the key remains active | Treat this as a failed revocation, retry through the authorized path, and escalate if persistence remains unavailable; never report the key revoked |
| 0491 hot-table DDL cannot acquire its bounded lock | Lock or statement timeout aborts migration | Inspect table size and blockers, choose a reviewed maintenance window, and retry the migration; never bypass the timeout or infer partial success |
| Migration prevents rollback | Old worker fails against new schema | Rehearse compatibility and record forward-recovery steps before applying |
| Rollback reopens agent permission holes | Operator selects original A or a worker below the 0494 boundary because it can still drain rows | Forbid original A; retain forward-only 0491/0492/0493/0494 and use only digest-pinned fixed A with ComputeID disabled and all four generic mutations held at 503 |
| Source succeeds but users and agents cannot reach it | UI, CLI, SDK or hosted MCP still calls an old route, drops an argument or lacks a published compatible artifact | Trace each committed operation through the real UI/API/SDK/CLI/MCP call and recovery path; keep release blocked when a last hop is absent |
| Packages or guide get ahead of servers | Example method missing or endpoint unavailable | Publish verified versions only; test clean consumers and label previews accurately |
| Release deadline hides an external blocker | Partner/browser/issuer acceptance is still missing near October 1 | Keep owner and next action visible; escalate readiness decision rather than relabeling rehearsal as acceptance |

Stop candidate traffic immediately on cross-tenant access, secret/recipient leakage, accepted invalid proof, duplicate or incorrect charges, surviving access after revocation, corrupted/lost records, or production job effects outside the approved operating mode. Investigate sustained error, latency or queue regressions against the captured baseline before expanding traffic. Preserve evidence and route traffic back to the retained compatible release; do not erase history.

## Alternatives considered

- **Merge all changes now and soak main later:** not recommended under current unpaused deployment settings. A reviewed deferred-manifest path exists, but it requires complete release holds and honestly deferred evidence; it does not remove any soak obligation.
- **Soak T1/T2, merge them, then soak T3:** use only for genuinely independent changes with their own release value. It is a poor fit for this stack because lower-tier work depends on T3 changes and a second integrated qualification would still be needed.
- **One frozen combined highest-tier candidate:** recommended. It tests the actual product that will ship, preserves the founder's combined release, and avoids multiplying clocks and CI runs. It does not waive individual acceptance criteria or production observation.

This is a planning recommendation, not an approval record or evidence that any merge, deployment, migration, soak or release has occurred. Independent review and the final execution-specific manifest are still required.
