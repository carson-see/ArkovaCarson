## The migration chain — replayed to current `main` head, byte-exact where possible

(`POST /v1/projects/{ref}/database/query`), each file read from `origin/main`

Disclosed deviations, same class as the 2026-08-21 FERPA replay:

1. **Three files were NOT applied byte-exact** — ` CONCURRENTLY` was stripped, because
   `CREATE INDEX CONCURRENTLY` cannot run inside the transaction the Management API wraps
   every request in (SQLSTATE 25001):
   - `0366_scrum2940_anchors_folder_id_index.sql` (file md5 `14d46ba6…`, payload md5 `a0c5af2d…`)
   - `0381_docusign_envelope_metadata_lookup_indexes.sql` (file md5 `9035e623…`, payload md5 `fc2d92ab…`)
   - `0389_anchors_ce_registry_ctid_partial_index.sql` (file md5 `0730beb1…`, payload md5 `c44e21af…`)

   On a greenfield rig the resulting index is identical — `CONCURRENTLY` changes the
   locking strategy while building on a live table, not the object. **Correction to the
   FERPA stand-up's record:** that doc states only `0381` required the strip. Measured
   here: `0366` and `0389` also carry active (non-comment) `CREATE INDEX CONCURRENTLY`
   statements. The other 109 files went in verbatim (baseline's two `CONCURRENTLY`
   occurrences are `REFRESH MATERIALIZED VIEW CONCURRENTLY` inside a function body —
   text, not executed at apply time).

2. **Ledger rows were inserted by this replay** — provisioning a brand-new isolated
   project to a known head, not repairing shared staging. Rows were written with the
   numeric prefix as `version` at insert time, so the §0-rule-10 reconciliation is a
   verification, not a repair: final readback `{"n":112,"head":"0414"}`.

3. **`0414` is not in the #2291 checkout** (the branch predates it; `main` gained it
   after). It IS in the prod ledger (prod head is `0414`), so the preflight's divergence
