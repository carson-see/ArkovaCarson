## 2. Root cause: `ENABLE_BATCH_ANCHORING` was never seeded on this rig

`services/worker/src/jobs/batch-anchor.ts:612-625`:

```ts
export async function processBatchAnchors(opts: ProcessBatchAnchorOptions = {}): Promise<BatchAnchorResult> {
  const EMPTY: BatchAnchorResult = { processed: 0, batchId: null, merkleRoot: null, txId: null };

  // S3-P0 / AC7: hard enablement gate. ENABLE_BATCH_ANCHORING is a DB-backed
  // switchboard flag (env fallback, fail-closed — flagRegistry.getFlag returns
  // false for unknown/unloaded flags). OFF ⇒ the job cannot claim, sign,
  // broadcast, or reconcile — even under ?force=true. ...
  if (!flagRegistry.getFlag('ENABLE_BATCH_ANCHORING')) {
    logger.info('Batch anchoring disabled (ENABLE_BATCH_ANCHORING off) — skipping batch run');
    return EMPTY;
  }
  ...
```

`EMPTY` is byte-for-byte the body observed at both flush fires. The gate is unconditional and
explicitly documented to override `?force=true` — this is deliberate, deployed safety behavior,
not a bug in the gate itself.

**`flagRegistry` resolution mechanics** (`services/worker/src/middleware/flagRegistry.ts:105-142`):
`ENABLE_BATCH_ANCHORING` is a `DB_FLAGS` entry — at boot, the registry queries
`switchboard_flags` for a matching `flag_key` row; if absent, it falls back to
`process.env.ENABLE_BATCH_ANCHORING === 'true'`. `getFlag()` returns `false` for anything not in
its in-memory map at all (fail-closed). This snapshot is taken once at process start;
`refreshDbFlag()` has zero callers, so a later flag write would not take effect without a restart —
moot here since neither source ever held a `true` value on this rig.

**Both sources verified empty, independently, this session:**

- **DB row absent.** `select flag_key, enabled from switchboard_flags` against
  `krhegsltjkazuomynbww` (Supabase MCP, read-only) returns exactly two rows:
  `ENABLE_ORG_CREDIT_ENFORCEMENT=false`, `ENABLE_VERIFICATION_API=true`. No
  `ENABLE_BATCH_ANCHORING` row exists.
- **Env fallback absent.** `gcloud run services describe arkova-worker-consolidated-mm-2026-08-staging
  --project arkova1 --region us-central1` shows no `ENABLE_BATCH_ANCHORING` env var on the container
  spec (only `ENABLE_PROD_NETWORK_ANCHORING=true` among anchoring-related vars).

**Confirmed live in the worker's own logs, at the exact millisecond of both flush fires**
(`gcloud logging read`, Cloud Run revision logs, `arkova1`):

```
2026-08-31T03:04:55.973763Z  Batch anchoring disabled (ENABLE_BATCH_ANCHORING off) — skipping batch run
2026-09-01T03:05:35.074960Z  Batch anchoring disabled (ENABLE_BATCH_ANCHORING off) — skipping batch run
```

Both lines land inside the same second as their respective `daily_flush_observations` `fired_at`
timestamp (`03:04:55Z` / `03:05:35Z`). This is not an inference from an empty response body — it is
the worker's own gate log, read directly.

**The rig-wide pattern is broader than this one flag.** The same log window shows three more
switchboard-gated subsystems silently no-op'ing for the identical reason (empty `switchboard_flags`
on this rig):

```
Revocation processing disabled via switchboard flag
Daily queue digest disabled; set ENABLE_QUEUE_DIGEST=true to enable
Ingestion refused: no ENABLE_PUBLIC_RECORDS_INGESTION row in switchboard_flags — this environment was never configured
```

**The provisioning scripts only seed one flag, and say so.** `scripts/staging/
seed-baseline-fixture.sql` inserts exactly one `switchboard_flags` row —
`ENABLE_VERIFICATION_API` — with an explicit comment acknowledging the fail-closed hazard for
*that* flag specifically ("without an enabled row, get_flag fails closed and every `/api/v1/*`
request returns a sub-10ms 503") and a preflight assertion that checks it. No equivalent seed or
preflight check exists for `ENABLE_BATCH_ANCHORING` (or for `ENABLE_QUEUE_DIGEST` /
`ENABLE_PUBLIC_RECORDS_INGESTION`, which failed the same way in these logs). `scripts/staging/
provision-isolated-rig.sh` seeds env vars for network/signing mode (`USE_MOCKS`,
`ENABLE_PROD_NETWORK_ANCHORING`, `ENABLE_AI_FRAUD`, `ENABLE_AI_REPORTS`) but never
`ENABLE_BATCH_ANCHORING`.

**This is a known, previously-documented failure class, not a novel one.** `services/worker/src/
jobs/agents.md` and `scripts/staging/agents.md` both describe the identical failure on an earlier
rig: *"rig #1417 SELF-SKIPPED (batch cron hit its entrypoint but no-op'd on the PR's own
`ENABLE_BATCH_ANCHORING=off` gate, so Merkle/intent-persist/reconcile ran ZERO times)"* — which is
exactly why `scripts/staging/batch-drain-harness.ts` and the `anti-hollow-soak` CI guard
(`scripts/ci/anti-hollow-soak/`) exist. Despite that tooling existing, the consolidated-mm
provisioning path (`provision-isolated-rig.sh` → `seed-baseline-fixture.sql`) still does not seed or
preflight-check `ENABLE_BATCH_ANCHORING`, and this soak reproduced rig #1417's exact failure mode.

The seed script's own comment explains why it exists: without ≥1 `SUBMITTED` anchor, a fresh rig
is classified `fixture_seeded` rather than `clean_mirror` by the honesty preflight — it is there to
satisfy that preflight check, not to exercise the drain. Direct query of `anchors` on this rig
confirms the status distribution is exactly what a fully-gated-off drain plus a static seed row
predicts, and nothing else:

```

SUBMITTED:      1   (the seed fixture above)
BROADCASTING/SECURED: 0
```

Batch-anchor conversion of the load-injected traffic is cleanly **zero for 13,204**, not partial —
consistent with the drain never having attempted a single claim.

## 4. Is this a merged-main code defect, or a rig-only gap?

**Rig-only gap, confirmed by direct comparison against prod in the identical window.** Prod's
`switchboard_flags` row for the same key, read live (read-only) from `vzwyaatejekddvltxyye`:

```
flag_key: ENABLE_BATCH_ANCHORING   enabled: true   updated_at: 2026-07-17 17:36:04+00
```

And prod's own anchor throughput in the exact soak window was healthy — not stalled:

```
select count(*) from anchors where status='SECURED'
  and updated_at between '2026-08-30T15:46:33Z' and '2026-09-01T15:46:33Z';
→ 13,711 SECURED
```

Prod ran its nightly 3am drain through the identical `processBatchAnchors()` code path (same head
family — prod `0440ce7e5` is an ancestor of the soak's `b2a65edd`) and secured 13,711 anchors in the
same 48h window the isolated rig secured zero. `scripts/ci/config-drift/expected-prod-config.json`
and `prod-config-snapshot.json` both assert `ENABLE_BATCH_ANCHORING: true` for prod, consistent with
the live read. The gate itself (`batch-anchor.ts:622`) is doing exactly what its own comment says
it is designed to do — refuse to claim, sign, or broadcast when the flag is unset, specifically so a
misconfigured environment cannot silently touch the treasury. That is correct, deliberate behavior,
not a bug.

**Conclusion: this is a soak-harness / rig-provisioning limitation, not a defect in merged main's
batch-anchor/flush pipeline.** The mechanism is fully specific and verified (missing DB row +
missing env fallback, confirmed by direct query, live logs, and a working prod comparison in the
same window) — this is not an "absence of evidence" call.

## 5. Severity

**Not a P0 code defect.** No fix to `services/worker/src/jobs/batch-anchor.ts` or the flush route
is warranted or safe — the gate is intentional treasury-safety behavior, prod has the flag on, and
prod's own drain ran normally throughout the window.

**But the practical consequence for THIS soak's evidence is severe, and is not softened by the
above.** The consolidated-mm soak's entire reason for existing is `RC-2026-08-22-deferred-
basedrift-exit`'s `pause_lift_obligation`: "a consolidated soak of merged main at the accumulated
head MUST run" before `DEPLOY_WORKER_PAUSED` flips. Several of the 19 PRs that manifest admits are
directly in or adjacent to the anchoring/credit/queue path this gate blocked from ever running (e.g.
#2251 org-quota rate-limit denial, #2266 `publicRecordAnchor` hardening, #2272/#2276 queue and
platform-health digest cron, credit-adjacent surfaces per the fee/credit model). This soak produced
**zero** coverage of: the Merkle-tree batch build, treasury signing, broadcast, `anchor_txid_journal`
persistence/reconcile, or the size/age triggers themselves — not degraded coverage, none. Per
CLAUDE.md §1.12, generic synthetic load that does not cover the changed path requires either
targeted staging/E2E evidence or an explicit Carson-approved residual-risk exception, neither of
which exists here for the batch-anchor surface.

File as a soak-harness **Task** (not a Bug — no main-code defect to fix), epic SCRUM-3373: extend
`scripts/staging/provision-isolated-rig.sh` / `seed-baseline-fixture.sql` to seed (or explicitly
verify) `ENABLE_BATCH_ANCHORING=true` — and ideally `ENABLE_QUEUE_DIGEST` /
`ENABLE_PUBLIC_RECORDS_INGESTION`, which failed the same way in the same logs — the same way it
already seeds and preflight-checks `ENABLE_VERIFICATION_API`, so that a future T3 consolidated soak
does not silently reproduce rig #1417's failure a third time.

## 6. `pause_lift_obligation` — go/no-go

**No-go. This soak's evidence does NOT satisfy the `pause_lift_obligation`** in
`docs/staging/rc-manifests/rc-deferred-2026-08-22.json`. The obligation requires a consolidated
soak that validates merged main's integrated behavior before `DEPLOY_WORKER_PAUSED` flips; the one
surface this soak needed to validate most — the chain-anchoring/batch-drain pipeline that several
admitted PRs touch — was never exercised at all, for the rig-provisioning reason documented above.
289/289 passing on health/API/cron/isolation probes is real, valid evidence for those surfaces, but
it is not a substitute for chain-path evidence, and should not be read as if it were.

**Recommended path to close the obligation:** re-run (or extend) the consolidated soak on a rig
provisioned with `ENABLE_BATCH_ANCHORING=true` confirmed via the preflight before the clock starts,
sized to actually exercise `triggerA_shouldFireOnSize` / `triggerB_shouldFireOnAge` /
`persistTxidJournal` / `recover_stuck_broadcasts` against the current head. `scripts/staging/
batch-drain-harness.ts` exists for exactly this and was not run against this rig.

This is a recommendation for the CTO's pause-lift decision, not a decision — the lift itself is not
made here.
