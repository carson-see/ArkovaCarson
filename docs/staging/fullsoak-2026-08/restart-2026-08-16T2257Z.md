# Rig instance recycle — 2026-08-16T22:57:05Z

**Not a fault, not an R2 trip, and the detection chain worked. Details below so the
uptime discontinuity in the evidence is explained rather than discovered later.**

## What happened

Worker uptime dropped from 239,010s (22:30Z reading) to 258s (23:01Z reading). Cause,
from the platform's own log:

```
22:57:05  INFO  Starting new instance. Reason: MANUAL_OR_CUSTOMER_MIN_INSTANCE
                — customer-configured min-instances or manual scaling.
22:57:16        Worker service started
22:57:22        Using BitcoinChainClient (signet)      <- boot line
22:57:57        Received shutdown signal               <- OLD instance, 52s later
```

Cloud Run started a replacement instance and then drained the old one. The new instance
was serving **52 seconds before** the old one was signalled, so there was no gap in
availability. Zero `ERROR`-severity logs in the window.

Unchanged throughout: revision `arkova-worker-fullsoak-2026-08-staging-00013-mrw`, image
digest, `git_sha f5d1070fcca2`. No deploy, no config change, no crash, no OOM.

## R2 assessment — not tripped

R2 restarts the soak day on **more than one restart per 24h**. Every instance start since
clock start (2026-08-12T15:51:30Z):

| Timestamp | Reason |
|---|---|
| 2026-08-14T03:52:14Z | `MANUAL_OR_CUSTOMER_MIN_INSTANCE` |
| 2026-08-14T04:06:38Z | `MANUAL_OR_CUSTOMER_MIN_INSTANCE` (14 min later) |
| 2026-08-16T22:57:05Z | `MANUAL_OR_CUSTOMER_MIN_INSTANCE` |

Three total. The 2026-08-14 pair was two inside 15 minutes and is already recorded in
`R2-DEVIATION-2026-08-14.md`. **Today's event is one restart in 24h, so R2 does not fire.**

## Detection worked — both layers

- **90-minute health check**: caught it immediately. `A1.2 uptime monotonic (no restart)`
  → **FAIL**, `SOC2_HEALTH: FAIL (14 pass / 1 fail)`. This is the assertion doing its job.
- **GCP alert policy** `PAGE — SOAK rig cold start`: its log-match condition
  (`jsonPayload.msg="Using BitcoinChainClient (signet)"`) matched at 22:57:22, and the
  `alert-delivery-proof` topic recorded a publish at **22:59:00**. The alarm fired and
  delivered.

**Correction, recorded deliberately:** I first reported the alarm as not having fired. That
was wrong. I queried a subscription name that does not exist (`soak-alert-proof-sub`; the
real one is `alert-delivery-proof-sub`), got an empty result, and read the emptiness as
evidence of absence. The authoritative signal is the topic's publish count, which shows the
message. This is the second time this session that an empty read of this channel was
misinterpreted — **an empty Pub/Sub pull is never proof an alarm did not fire**, because
pulls race with other consumers and a wrong resource name returns the same empty result as
a quiet channel.

## Effect on the evidence model

Per `feedback_soak_clock_is_worker_uptime`, the soak clock's durable signal is Cloud Run
worker uptime. That signal is now discontinuous, so the pack **must not claim "N days of
continuous worker uptime."**

Continuity for this window rests on three things that *are* continuous and verifiable:

1. The pinned revision `00013-mrw` has served the entire window — never redeployed,
   digest and `git_sha` unchanged since Day 0.
2. Availability was unbroken across every recycle (overlapping instances; the uptime
   probes and `/health` assertions never failed for availability).
3. Every recycle is enumerated above with its platform-supplied cause.

State the clock as **elapsed wall-clock time against a pinned, continuously-available
revision**, with instance recycles disclosed — not as uninterrupted process uptime.
