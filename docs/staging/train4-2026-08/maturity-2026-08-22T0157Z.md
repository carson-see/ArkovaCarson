### Finding — `/jobs/platform-health-digest` returned 404 for the entire window, and the driver counted it as `ok`

The soak-start doc lists `/jobs/platform-health-digest` among the routes the driver covers,
and the pre-clock verification run concluded the union "introduces no regression on …
the cron routes." In fact that endpoint answered **404 on all 120 in-window requests**.

**It is not a train regression.** `git grep` at the union head `0333464d…` finds
`platform-health-digest` in **no file under `services/worker`** — only in two docs. It is
equally absent from current `origin/main`. The route belongs to a **wave3** member that has
not merged; on the wave3 rig revision `00004-cjk` the same probe returned **200 × 93**
during the wave3 window. TRAIN-4's union simply does not carry the route, so 404 is the
correct answer.

**What is a defect is the legibility.** The driver's classifier counts any 2xx–4xx that is
not 401/403 as `ok`, so 120 requests against a route that does not exist were reported as
successful coverage of a cron surface. This is the same failure class as FD-WAVE3-1
(401 counted as success) and FD-PROBE-1 (an anonymous 401 taken as proof a route exists),
one step further out: **a 404 taken as proof a route works.** Of the two cron routes the
driver claims, only `/jobs/queue-digest` (200 × 122) contributed real coverage. No member of
this train touches either digest route, so no member's evidence depends on it.

## Requirements of §1.12 that this window did NOT meet

Stated here rather than left for a reader to discover:

- **No preflight was run for this window** (above). The gate's `Preflight result` /
  `Preflight timestamp` fields are satisfied in the per-PR blocks by an explicit
  `### Residual-risk note`, which is the mechanism §1.11A provides for exactly this case —
  not by importing another window's reading.
- **Deploy rollback rehearsal was never run.** §1.12 requires it at T2. The prior revision
  `00004-cjk` (created 2026-08-20T16:40:21Z) remains on the service as the untested rollback
  target — and note it is **not** "this train minus the members": it runs a different image
  family (`arkova-worker@sha256:90ea4e06…`, the shared worker) built from the **wave3**
  union, which carries at least one route this tree does not have. A rollback from
  `00005-rib` to `00004-cjk` would therefore be a jump to a different code line, not a clean
  revert. This makes the missing rehearsal more material than usual and it should be closed
  before these PRs are readied.
- **No `public.staging_deploy_log` row exists.** The rig was deployed with a direct
  `gcloud run deploy` on a digest-pinned image; `scripts/staging/deploy.sh` is hard-scoped to
  the shared `arkova-worker-staging` service and never wrote a row. There is also **no Cloud
  Build id** to cite in its place: the image was built locally with `docker buildx`
  (`desktop-linux` driver) — the build record is `~/arkova-soak-evidence/train4/build.log`
  and the Artifact Registry digests it produced.
- **No E2E suite was run against this rig.** The per-PR blocks cite each PR's CI E2E result
  at its frozen head, which is a different thing and is labelled as such.

Migration rollback/reapply proof is **not** owed: no member of this train touches
