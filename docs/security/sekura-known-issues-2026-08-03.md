## By design — not findings

These are product decisions, not defects. Reporting them as vulnerabilities will not be accepted as findings, though we will happily discuss any case where you think the design itself is wrong.

1. **Cross-tenant public reads on the search and verify surfaces are intentional.** Arkova is a public-records verification product. `search.arkova.ai`, the public verify page, the embeddable badge/widget, the anonymous `public.get_public_anchor()` / `get_public_anchor_by_fingerprint()` RPCs, `GET /api/v1/verify/:publicId`, and `GET /api/v1/credentials/:publicId/ctdl` are all **designed** to answer for records belonging to organizations other than the caller's. An anonymous or cross-org read succeeding on these endpoints is the product working. Do **not** report it as a tenant-isolation finding. What *is* in scope on these surfaces: whether the projection publishes a field it should not (see KI-07 for the one residual we have already accepted), whether a non-`SECURED` or soft-deleted record can be surfaced, and whether internal identifiers (`user_id`, `org_id`, `anchors.id`) leak in place of `public_id`.
2. **Supabase RLS is the tenant-isolation boundary, and the service-role key is server-only.** Tenant separation is enforced in Postgres by row-level security with `FORCE ROW LEVEL SECURITY`, not by application code paths — so an RLS bypass is a genuine finding and a missing UI check on top of correct RLS generally is not. The `service_role` key exists only in the worker and in Secret Manager; it is never shipped to the browser. If you find it reachable from a client, that is a critical finding and we want an immediate heads-up rather than a write-up.
3. **Terminology constraints in UI copy are deliberate.** User-visible strings never say Wallet, Gas, Hash, Block, Transaction, Crypto, Blockchain, Bitcoin, Testnet, Mainnet, UTXO or Broadcast; they use Fee Account, Fingerprint, Network Receipt, Production Network and so on. This is a legal and brand decision enforced by a CI lint, not obfuscation or security-through-naming. Internal code, API field names and log lines use the technical terms freely. Do not report the naming divergence between the API and the UI as information hiding or as an inconsistency defect.
4. **`/api/v1/*` rate limits are tier-dependent by design**: 100 req/min per IP anonymous, 1,000 req/min per API key, 10 req/min for batch, with `Retry-After` on 429. Observing that an API key gets a higher ceiling than an anonymous caller is intended behaviour.
5. **Documents never leave the browser, and we would like this challenged.** Fingerprinting, OCR and PII stripping all run client-side; only PII-stripped metadata and the fingerprint reach the server. The one carve-out is connector-fetched documents (DocuSign / Google Drive), which are hashed in memory server-side and discarded, with logger redaction, type-based Sentry scrubbing, and a CI lint blocking document bytes from reaching any logger or `Error`. We traced this end to end and believe it holds. It is listed here as an assertion to disprove, not as an area to avoid — if it does not hold, that is the single most valuable thing you could tell us.

## Coverage caveats

Read the list above as "everything we know that we could reach from a named source", not "everything that exists". Specifically:

- **SonarCloud coverage is not clean, it is stale.** SonarCloud runs Automatic Analysis rather than a CI scanner, and **main-branch analysis has been dead since 2026-05-06** — every Compute Engine task since then is a pull-request analysis, so all main-branch issue counts and the quality-gate status are a stale 2026-05-06 snapshot. Do not read the absence of open SonarCloud issues on `main` as evidence of anything. Two further limits compound this: autoscan imports no test coverage at all, and `.sql` files are parsed by the Oracle PL/SQL analyzer rather than a Postgres one, so all SQL findings are dialect-mismatched noise and migrations are now excluded outright. In addition, **the SonarQube MCP server was not connected in the session that compiled this document**, so no live issue or hotspot query was run — the statements here come from a 2026-08-01 verification against the SonarCloud REST API, not from a fresh query today. Treat SAST on our side as effectively unrun since May and scope your own static analysis accordingly.
- **The Confluence briefing this document accompanies is dated 2026-08-01 and is founder-review-pending.** Where the two disagree, this document is newer: a substantial batch of security fixes merged and deployed on 2026-08-02 and 2026-08-03, and they are reflected in the "Already fixed" section above. The briefing does not carry the DMARC item (KI-08); it is disclosed here.
- **Not every issue in our tracker is scored.** Jira priority is present on Bug-typed issues; several items came from the Confluence briefing or a live audit and were recorded without a severity. Those cells say "Not scored" rather than carrying an invented number. Our internal severity bands and remediation SLAs are in [`docs/compliance/pentest-scope.md` §5](../compliance/pentest-scope.md).
- **Bug-log identifiers and Jira keys are two separate namespaces.** `BUG-YYYY-MM-DD-NNN` identifiers come from the Confluence [Bug Tracker — Master Log](https://arkova.atlassian.net/wiki/spaces/A/pages/88768514); `SCRUM-NNNN` are Jira issues. Most items carry both; a few carry only one. `F-N` identifiers are findings from our 2026-07-28 → 2026-07-31 launch soaks, recorded in `docs/staging/SOAK-FINDINGS-2026-08.md` and in the bug log, but never given individual Jira tickets.
- **We filtered aggressively to your scope.** Our open-bug set is considerably larger than 23 items; the remainder are CI, build-tooling, staging-rig, test-infrastructure and internal-process defects with no exposure on `app.arkova.ai`, the worker API, `edge.arkova.ai`, the search/marketing sites, or the `main` branch. They were excluded deliberately, not overlooked.
- **Some fixes are live in production ahead of their pull request merging.** Migration `0393` (the org-admin anchors UPDATE policy in KI-03) and migrations `0385` / `0387` are applied to production while their PRs are still open. Never infer production state from PR status in either direction — we verify against the database, and so should you.
- **Third-party platform internals are out of scope** (Stripe, Supabase hosted infrastructure, Vercel platform), as is volumetric denial of service and social engineering of personnel, per [`docs/compliance/pentest-scope.md` §3.2](../compliance/pentest-scope.md).
- **The target is live production with real customer data and a real Bitcoin treasury.** Please do not run destructive tests, bulk deletion, or sustained load without contacting us first. `anchor.status = 'SECURED'` records are anchored to the Bitcoin mainnet and are not reversible. The two test orgs contain synthetic data only; other orgs do not. If you find something actively exploitable against real customer data, stop and contact us immediately rather than continuing to characterise it — a fast heads-up is worth more to us than a complete write-up.
