## 3. The deploy-gate / merge-before-soak control (CTO ruling 2026-07-28)

**The problem this section exists to solve:** the Staging Soak Evidence Gate (a required Mergify check) hard-requires real soak fields for T1/T2/T3. A PR-body evidence block satisfies the pre-merge git hook (`.claude/hooks/check-staging-evidence-pre-merge.sh`) but NOT the CI gate — so even with every draft marked Ready, Mergify merges nothing above T0 for this wave. Verified live this session: #1721 and #1716 are clean on every required check except the soak gate.

A prior session correctly refused to build a bypass for this, on the grounds that merging unsoaked T2/T3 worker/migration code would auto-deploy to prod via `deploy-worker.yml`'s push-to-main trigger. **That objection is resolved, not overridden, by the following two-part control, built and shipped this session as [PR #1756](https://github.com/carson-see/ArkovaCarson/pull/1756):**

1. **Deploy gate** (`vars.DEPLOY_WORKER_PAUSED` in `deploy-worker.yml`). Pauses the actual Cloud Run deploy steps — build/scan/push image + `gcloud run deploy` — while leaving `pre-deploy-checks` (typecheck/lint/test/copy-lint) unconditional. Default is unpaused (fail-open to today's behavior); `workflow_dispatch` always bypasses for an intentional hotfix deploy; reversal is a single `gh variable set/delete`.
2. **`deferred_consolidated_soak` mode** (`scripts/ci/check-staging-evidence.ts`, `docs/staging/rc-manifests/rc-2026-08-launch-72h.json`). Lets a PR explicitly listed in the manifest pass the Staging Soak Evidence Gate WITHOUT real soak evidence — but ONLY when the gate can positively confirm (live, every run, fail-closed on ambiguity) that the deploy gate is actually engaged. If it cannot confirm the pause, deferred mode refuses to activate. The check's output always states plainly "DEFERRED and NOT satisfied" — never renders as evidence being present. `approval_status` on the manifest stays the literal `"pending"` for as long as `soak_mode` is set.

**This is the CTO ruling, recorded explicitly:** we are deliberately trading "evidence before merge" for "evidence before DEPLOY." **Residual risk, stated honestly:** `main` will carry unsoaked T2/T3 worker/migration code for the duration of the soak window (from Wave M's first merge until soak #1 matures and the pause lifts). **Any hotfix needed during that window must go through the same deploy gate** — `workflow_dispatch` to force an intentional, reviewed deploy of the exact fix, never a silent bypass of the pause. This is why §4 below maps this control explicitly to CC8.1 (change management) — it is the auditable artifact that the change-before-verification trade was a deliberate, reviewed, reversible decision, not an accident.

**Sequencing this unlocks (`wave-merge-choreography-2026-08.md` §0.1/§0.2):**
```
1. vars.DEPLOY_WORKER_PAUSED=true set on the repo (BEFORE Wave M's first merge)
2. docs/staging/rc-manifests/rc-2026-08-launch-72h.json soak_mode="deferred_consolidated_soak" (done, this session, companion push to PR #1733)
3. Wave G→M→D→F→S merge per the choreography doc, citing the manifest per PR
4. main carries the full integrated wave, deploy still paused
5. 72h signet integration soak (§1, this document) runs against that integrated head
6. Soak matures → manifest returns to normal (soak_mode removed, real evidence filled, approval_status="approved")
7. DEPLOY_WORKER_PAUSED unpaused → single verified deploy → prod-enablement flag flips (prod-enablement-checklist-2026-08.md)
```

## 5. The 4-pillar evidence standard as end-to-end journeys

Per `memory/feedback_soak_evidence_standard.md`: durability = VOLUME + CONCURRENCY (pgbench-style) + EDGE CASES + ISOLATION, empirical, never "one seed + one trigger." The 72h-soak-runbook's own §5 already specifies per-surface exercises correctly — **this section's addition, per the founder's scope correction, is to chain those exercises into cross-feature JOURNEYS that a single merged PR's soak evidence cannot see**, because the point of a consolidated 45-day soak is exactly the interaction between features that individually passed in isolation.

### 5.1 Primary journey — "connector document to verified, folder-filed, billed anchor"
Exercises §2.2 (DocuSign) + §2.10 (bulk/mixed-format) + §2.1 (anchoring core) + §2.3 (folders) + §2.4 (credits) + §2.5 (webhooks) + §2.6 (verification API) in one chain:
1. DocuSign envelope completes on a connected org → the org's Completion-queue-mode rule fires (verify #1711's auto-seed actually applied the rule without manual admin action) →
2. the envelope lands in BOTH the correct member's queue AND the org queue (not just one) →
3. the daily drain (or manual trigger for soak-timing purposes) anchors it →
4. exactly one credit deduction occurs (`ENABLE_ORG_CREDIT_ENFORCEMENT=ON` in the rig per R17 — verify no double-charge even though prod runs this flag OFF; the rig is the ONLY place this path gets real evidence before G3) →
5. the outbound webhook fires exactly once (`ENABLE_OUTBOUND_WEBHOOKS=ON` in the rig) with a `delivery_log` row →
6. the anchor verifies independently via the public verify page AND `/api/v1` (both surfaces, since the dual-OpenAPI-spec finding means they can drift) →
7. the proof materializes (or the DRY-RUN preflight confirms it WOULD, per §2.12's constraint) →
8. it appears filed in the correct folder (§2.3's UI, not just the hook).

A break at any numbered step is a cross-feature regression that no single PR's isolated soak evidence could have caught — this is the concrete meaning of "a journey crossing five merged PRs is worth more than five isolated checks."

### 5.2 Secondary journey — "mixed-format bulk batch across every surface"
