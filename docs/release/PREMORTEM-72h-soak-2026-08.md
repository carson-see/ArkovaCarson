# Pre-Mortem — The 72h Soak Itself, 2026-08 Launch

> **Framing:** it is 72+ hours from now. The soak clock ran out. The evidence it produced is worthless, or the soak never meaningfully started. This document works backwards from that assumption to name every mechanism that gets there, and what has to be true for it not to happen.
> **Distinct from:** `RELEASE-PLAN-2026-08-FINAL.md` §8, which pre-mortems the *launch* failing (security bypasses reaching prod, legal findings, KPI shortfalls). This document pre-mortems the *soak as an instrument* failing — producing a result that looks like evidence but isn't.
> **Sources:** `72h-soak-runbook-2026-08.md` (especially §0.6–§0.9), `RELEASE-PLAN-2026-08-FINAL.md` §1/§3/§5/§8, `wave-merge-choreography-2026-08.md` §0.1/§0.2, `CLAUDE.md` §1.11/§1.11A/§1.12, `sprint-2026-07-28-findings.md`, HANDOFF.md 2026-07-28 entry, `memory/feedback_soak_evidence_standard.md`, `memory/feedback_soak_clock_is_worker_uptime.md`, `memory/feedback_frozen_soak_head_not_orphan.md`.

## 1. Hollow soak — the rig runs but exercises nothing

**Mechanism:** a rig can be provisioned, pass its clean-mirror preflight, run for the full window, and produce a green uptime number while never actually exercising the code paths the soak exists to validate. **This has already happened once**, per the founder's explicit framing for this document: the fired-team's 48h B1 soak ran with the batch flag OFF, scheduler OIDC missing, and treasury unfunded — the rig was up, the clock ran, and none of it proved anything. 48 hours were spent producing a green checkmark with no evidence behind it.

The runbook's own history shows a milder version of the same failure recurring: the `maxsoak-154f9ff2` rig (2026-07-23) started with **0 anchors and 0 Cloud Scheduler jobs — "pure idle uptime, not evidence"** (HANDOFF, 2026-07-23 entry) before a dispatched agent seeded real traffic. That was caught because someone checked; it would not have been caught by the clock alone.

**Earliest observable signal:** the T+0–2h smoke gate (§0.7 of the runbook) is designed to catch this specifically — "First anchor SECURED end-to-end," "5 Cloud Scheduler jobs show ENABLED and at least one successful run each," "5xx rate = 0." If any of those boxes is unchecked at T+2h, the rig is hollow and the runbook's own rule is explicit: "stop, fix, redeploy if needed... re-run the T+0–2h gate from zero." The danger is not that the gate doesn't exist — it does, and it is well-designed — the danger is that under time pressure (Aug 10 is a hard date) someone treats a partially-checked gate as "close enough" and proceeds to burn the remaining 70 hours anyway.

**What guarantees this time is different:** the runbook's §0.7 T+0–2h gate is a hard stop with named, checkable boxes, not a narrative checklist — it is more mechanical than the July 23 rig's own smoke check was. But a checklist only works if someone runs it and is willing to actually restart the clock on a fail. The `ENABLE_ORG_CREDIT_ENFORCEMENT=ON` / `ENABLE_OUTBOUND_WEBHOOKS=ON` divergence (R17) is itself a hollow-soak risk in miniature: if either flag silently reverts to the rig's inherited-from-prod default (`false` for both) because the flag-mirroring step was skipped, the credit-conservation and webhook-delivery pillars will "pass" by doing nothing, exactly like the fired-team soak.

**Mitigation:** treat the T+0–2h gate as load-bearing, not a formality — do not let "provisioning succeeded" be read as "smoke gate passed." Explicitly re-verify the two R17-divergent flags (`ENABLE_ORG_CREDIT_ENFORCEMENT`, `ENABLE_OUTBOUND_WEBHOOKS`) are `ON` on the rig via `gcloud run services describe` at T+0, not just at provisioning time — a redeploy or config drift between provision and clock-start could silently reset them. **Owner:** RTE (executes the gate), Carson (does not authorize soak maturity without seeing the T+0–2h artifact).

## 2. Clock invalidated mid-run — a new commit, a redeploy, or config drift voids exact-head evidence

**Mechanism:** per `CLAUDE.md` §1.11A, "any runtime, migration, or tested-code commit after a soak invalidates exact-head evidence and requires a new soak or an explicit residual-risk note." The 72h soak's frozen head (`train_launch_sha`/`build_sha_baked`) is meant to be picked once and never floated mid-soak (runbook §1: "Do not float the head mid-soak"). But this wave has a structural reason a commit could land mid-soak anyway: the `deferred_consolidated_soak` mechanism (PR #1756) exists specifically so Wave M/D/F/S PRs can keep merging to `main` *while the soak runs*, because the deploy gate — not the soak — is what's supposed to keep unsoaked code out of prod. If the rig's image is ever rebuilt from a newer `main` mid-window (intentionally, to "catch up" the soak to the latest merges, or accidentally, by a redeploy script defaulting to `main` instead of the pinned SHA), the clock silently resets without anyone declaring it reset.

**Earliest observable signal:** `gcloud run revisions describe <revision-id>` shows a new revision ID or a changed image digest mid-window when nobody intended a redeploy; the continuous "Worker restart" monitor (§0.7) fires on any restart at all, which is a proxy signal but doesn't by itself distinguish an intentional pinned-image redeploy from an accidental head-drift redeploy.

**Mitigation:** the runbook already states the rule (a restart resets the clock, full stop, no partial credit) — the actual risk is *not noticing* a restart happened, especially across a multi-day, multi-session soak (see §9 below). The continuous "Worker restart" monitor polls every 5 minutes specifically so this can't be missed by a human checking once a day. The image digest recorded in the manifest's `environment.image_digest` at provisioning time must be re-diffed against the live revision's digest at every gate checkpoint (T+2h, T+6h, T+24h, T+48h, T+72h), not just checked once at go/no-go. **Owner:** RTE (owns the per-gate digest re-check; this should be added explicitly to the daily observation checklist commands in §0.7 if it isn't already mechanically scripted).

## 3. The rig is not a clean mirror

**Mechanism:** `CLAUDE.md` §1.11A is explicit that shared staging (`ujtlwnoqfhtitcmsnrpq`) is merge-grade only when `staging-honesty-preflight.ts` reports `environment_type=clean_mirror`, and that `soak_artifact`, `fixture_seeded`, timestamp migration rows, duplicate migration names/versions, or unexplained prod divergence invalidate a project for new merge evidence. This soak deliberately avoids shared staging (its own isolated rig, `launch-72h-2026-08`), which sidesteps the shared-contamination risk this rule mainly targets — but the isolated rig has its own contamination surface: the migration ledger collision already found this sprint (finding #26, `sprint-2026-07-28-findings.md`: "#1739 and #1741 BOTH claimed `0375`... the reservation protocol relies on agents re-reading `agents.md` on origin/main, but parallel agents can claim within the same window") could recur on the rig itself if the wave's Wave-S PRs are still opening (as the choreography doc warns, repeatedly) while the rig's migration train is being assembled.

**Earliest observable signal:** the preflight (`staging-honesty-preflight.ts --format json`) reporting anything other than `clean_mirror`, or a re-run of the preflight after a post-freeze migration lands (runbook §2b explicitly calls for a re-run "if any migration lands on the rig after the first pass" — the risk is this re-run being skipped because it feels redundant with the one the provisioning script already ran automatically).

**Mitigation:** the runbook's own migration train order (§1 go/no-go: "0359 → 0360 → 0362 → 0364 → 0368 plus any newly appended numbers per the RTE table") is the actual contamination control here — every migration applied to the rig must trace to a specific, closed PR, not an ad hoc `db push` against whatever's in a local branch. Re-run the preflight after every migration application to the rig, not just once at provisioning, and treat a non-`clean_mirror` result mid-soak exactly as the stop-the-line rule in §1.11A demands: stop, do not repair/delete ledger rows to make it look clean, either rebuild or move to a new isolated project with explicit approval. **Owner:** RTE.

## 4. Evidence that cannot survive an auditor

**Mechanism:** this soak's stated audience is a SOC 2 Type 2 auditor (`RELEASE-PLAN-2026-08-FINAL.md` header). The runbook's §0.8 states the standard directly: "every artifact above must be timestamped and either (a) a raw command-output capture (not an agent's prose summary of what it saw), or (b) a git-tracked file with commit history as its own provenance record... a chat-log claim that 'the check passed' does not" satisfy the requirement. The failure mode is an evidence pack that reads convincingly in a session transcript but has no artifact an outside party could independently check — a paraphrase of a `psql` result instead of the redirected output file, a screenshot instead of a `gcloud` JSON dump, or an exception-register entry written from memory after the fact instead of at the time of the event.

**Earliest observable signal:** at T+72h exit, someone tries to assemble the evidence pack and finds gaps — a pillar exercise that was "run" but has no corresponding file in `docs/staging/launch-72h-2026-08/`, or an exception-register entry with a vague timestamp ("sometime around T+30h") instead of a real one.

**Mitigation:** the runbook's §9 evidence-artifact list and §0.8's continuity-control table already specify exact storage paths (`docs/staging/launch-72h-2026-08/`) and exact artifact types per control. The discipline required is boring but real: redirect command output to files as you go, not at the end from memory. The exception register (§0.8) is the single highest-value artifact for an auditor specifically because "an empty register at T+72h is a claim that must be true, not assumed true by omission" — meaning the register's absence of entries is only credible if the monitoring that would have populated it was actually running the whole time, which is its own separate risk (§9 below). **Owner:** RTE (captures artifacts in near-real-time, not retrospectively), Carson (spot-checks a sample of artifacts against their claimed content before attesting at T+72h exit, not just checking the artifacts exist).

## 5. Passing for the wrong reason — synthetic load that doesn't touch the changed surfaces

**Mechanism:** `CLAUDE.md` §1.12 states this exactly: "generic synthetic load is supporting worker-health evidence only, and if it does not cover the changed path, the PR must include targeted staging/E2E evidence." This is a **documented past failure**, not a hypothetical — the fired-team B1 soak (§1 above) is one instance, and more generally a soak that hits `/health` and a generic anchor-creation loop for 72 hours proves the worker doesn't crash under load, which is a real but narrow claim, easily mistaken for "the wave's changes are validated."

The runbook's own §5 addresses this directly and names the specific changed surfaces this wave needs covered: mixed-format bulk anchoring through `/api/v1/anchor/bulk` (not just single-anchor creates), the 22-format extraction matrix, the SCRUM-3031 `batch_insert_anchors` regression check specifically (not generic anchor volume), the fixed `x-org-id` isolation check under concurrent load specifically (not a single-request smoke test), and both halves of the RPC-revoke migration (anon denied *and* the worker's own service-role path still functions — RELEASE-PLAN §8 item 9 explicitly warns against treating "anon correctly denied" alone as sufficient).

**Earliest observable signal:** at any gate checkpoint, the evidence produced is volume/uptime numbers with no corresponding artifact tied to a *named* changed surface — e.g., "1.2M requests served, 0.01% error rate" with no separate artifact showing the SCRUM-3031 repeat-submission scenario was specifically forced and timed.

**Mitigation:** the runbook's §5 already enumerates named per-surface exercises rather than a generic load target — the risk is a soak operator defaulting to whatever's easiest to script (a generic anchor-creation loop) because the named exercises take more setup. The T+6h/T+24h/T+48h gates (§0.7) require specific named checks (mixed-format bulk ≥100, SCRUM-3031 regression check, RPC-revoke both-halves check, isolation pillar under concurrent load) rather than a generic volume number, which is the actual mitigation already built in — the residual risk is operator discipline in actually running the named exercise rather than a proxy for it. **Owner:** RTE.

## 6. The soak succeeds but hides the 10k-DAU design ceiling

**Mechanism:** the runbook's own §0.6 states this as an open, named finding, not a risk to be discovered later: at 10k DAU (≈25,000 anchors/day derived), "the FIRST bottleneck" is the single nightly 3am batch-drain design (`BATCH_ANCHOR_MAX_SIZE=10000` per invocation, versus a projected daily volume that exceeds it on day one). A 72h soak running at **today's** traffic shape — not 10k-DAU shape — can report every gate green while never coming close to exercising the volume at which the drain design breaks. §0.6 is explicit that "a soak that never approached 250 concurrent sessions or 28 RPS quietly stand[ing] in for 10k-DAU evidence" is exactly the failure this section exists to prevent naming.

**Earliest observable signal:** the soak's own volume/concurrency numbers, honestly reported, show it never reached the A3–A5 targets (250 peak concurrent sessions, ≈28 RPS sustained / ≈83 RPS burst). The runbook explicitly requires recording "whether it reached A3–A5's numbers explicitly" — if that line in the evidence pack is blank or fudged, this failure mode is live.

**Mitigation:** this is not fixable inside the 72h window as currently scoped — the runbook is honest that the soak is "scoped to the current 45-day-merged surface at today's traffic shape; it is not, by itself, a 10k-DAU load test." The actual mitigation is two named, still-open verification items from §0.6: the DB connection ceiling (an unverified real number — `max_connections` against prod, plus Supabase pooler config) and the batch-drain redesign (multiple drain passes per night or an intra-day cadence). Neither is soak evidence; both are engineering work items that must be separately tracked and closed before any claim of "ready for 10k DAU" is made, soak-green or not. **Owner:** RTE/DBA (pulls the live connection-ceiling number), L1 (drain redesign, standing chain/treasury ownership).

## 7. Silent fail-open — credit/billing RPC failures that log but don't alert

**Mechanism:** `RELEASE-PLAN-2026-08-FINAL.md` §8 item 13 documents this in detail for PR #1758 / migration 0377 specifically: `deduct_ai_credits`'s caller (`ai-extract.ts:248-252`) **fails open** — if the RPC call fails, the code logs an error and proceeds with the extraction anyway, returning 200 to the user. `allocate_monthly_credits` and `roll_over_monthly_allocation` have "no fallback and no Sentry wiring" — a grep of `services/worker/src/utils/logger.ts` confirms the pino transport is not wired to Sentry and `Sentry.captureException` is not called from any of these RPCs' failure branches. The finding states plainly: "Sentry wiring is in flight; assume it may not land" for this soak's window. A soak that only checks HTTP status codes and 5xx rates will see none of this — every one of these failure paths returns 200.

**Earliest observable signal:** a `logger.error` line in Cloud Run logs matching `"falling back to..."`, `"failed twice"`, or `"proceeding with extraction"` during the soak's positive-path window — but only if someone is grepping for those exact strings, which is not the same as a monitor that pages. §0.7's continuous monitors table does not currently include a log-pattern monitor for these specific strings; it has a general "Sentry error-rate spike" monitor that is explicitly conditioned on Sentry being wired to the rig's environment ("confirm this is wired before the clock starts, or this monitor is a gap, not a check").

**Mitigation:** §5's EDGE CASES pillar and the RELEASE-PLAN's staged-verification recommendation (run the four credit-mutating positive-path tests in the first 6 hours, before load accumulates) is the closest thing to a mitigation currently specified, but it only catches a break if the soak operator is actively balance-checking, not passively watching for errors. Two concrete additions close this gap: (1) add a log-pattern continuous monitor for the specific fail-open strings named above, independent of whether Sentry wiring lands in time; (2) treat "money leaks with a 200 response" as its own abort-trigger class in §0.7's gate structure — currently the only zero-tolerance money trigger named is "credit-ledger conservation" drift at T+48h, which is a *cumulative* check and could miss a leak that's small-but-nonzero per transaction if the cumulative check's tolerance isn't actually zero in practice. **Owner:** RTE (adds the log-pattern monitor before clock start), L1 (owns the underlying fail-open code paths and the Sentry-wiring landing decision).

## 8. The deploy pause is forgotten

**Mechanism:** `vars.DEPLOY_WORKER_PAUSED=true` must be set before Wave M's first merge and must stay `true` for the soak's entire duration — the `deferred_consolidated_soak` gate mechanism's hard precondition is exactly this (`wave-merge-choreography-2026-08.md` §0.2: "the gate must positively confirm `vars.DEPLOY_WORKER_PAUSED === 'true'` on the live run... if the deploy gate isn't confirmed engaged, deferred mode refuses to activate"). Two opposite failure directions exist:

- **Left true too long:** `RELEASE-PLAN-2026-08-FINAL.md` §8 item 12 names this exactly — a real post-soak hotfix merges clean, CI is green, and prod never updates, because nobody explicitly un-paused after soak maturity. `revision-drift.yml`'s cron will eventually fire a Sentry alert, "but only if someone is watching for it."
- **Lifted too early (the mirror-image risk, not separately named in the source docs but symmetric):** if `DEPLOY_WORKER_PAUSED` is flipped to `false` mid-soak — by an unrelated PR, a manual `gh variable set`, or a process that doesn't know the soak is still running — every subsequent worker-touching merge auto-deploys **unsoaked** code straight to prod, defeating the entire point of the two-part control built this session (PR #1756). This is arguably the more dangerous direction of the two, because unlike the "forgotten paused" case, it is not self-announcing via a drift alert — it looks like a normal, successful deploy.

**Earliest observable signal:** for "left too long" — `revision-drift.yml` firing after the soak has matured and a real fix has merged. For "lifted too early" — a `deploy-worker.yml` run actually executing the `deploy` job (not just `pre-deploy-checks`) during the soak window; the §0.8 continuity control table already specifies checking `gh variable list` at every gate checkpoint specifically because a flip mid-soak "is itself a contamination event."

**Mitigation:** Gate G4 in `RELEASE-PLAN-2026-08-FINAL.md` §7 already names the un-pause as its own closing step with named owners (RTE executes, Carson authorizes) — "do not let 'the wave is soaked' alone count as done." For the early-lift direction, the per-gate `gh variable list` check specified in §0.8 is the control; it needs to be treated as a hard abort trigger (equivalent to a contamination event under §1.11A) if it's ever found `false` mid-window, not a note-and-continue. **Owner:** RTE (executes both the pause and the un-pause; checks the variable at every gate), Carson (authorizes the un-pause specifically, per the same pairing that authorized the pause).

## 9. Migration rollback never actually rehearsed

**Mechanism:** every migration in this wave carries a `-- ROLLBACK:` comment by convention (`CLAUDE.md` §4), and the runbook's go/no-go list includes "Rollback rehearsal completed and recorded for all five migrations above **before the clock starts** (not 'during' — rehearsal is a pre-soak gate, the soak itself observes forward-path behavior)." The risk is the gap between "the migration file contains a rollback comment" and "the rollback comment was actually executed against a real database and confirmed to restore working state." A `-- ROLLBACK:` block that was written but never run can contain a syntax error, a wrong table name, or an incomplete restoration (e.g., a `GRANT` rollback that misses one of six functions) that nobody discovers until an actual incident forces the rollback to run for real.

The one documented case this sprint where a rollback block *was* actually verified — PR #1758 / migration 0377 — shows what real verification looks like: "0377's `-- ROLLBACK:` block was read this session and restores `GRANT EXECUTE... TO anon, authenticated` on all six functions plus recreates `invite_member(uuid,text,text,uuid)` verbatim (captured via `pg_get_functiondef` pre-drop)... this matches the live pre-migration grant state queried this session exactly." That is closer to a real verification than a rehearsal (the rollback statement was read and cross-checked against the pre-migration state, not executed), and it is explicitly *not* the same as the apply→rollback→confirm→re-apply→confirm-idempotent cycle the T+48h gate (§0.7) calls for.

**Earliest observable signal:** the T+48h gate's checkbox "Rollback rehearsal (apply → rollback → confirm → re-apply → confirm idempotent) complete for all migrations in the train — not deferred to T+72h" is unchecked, or checked without a corresponding artifact showing the actual apply/rollback/reapply sequence and its output.

**Mitigation:** treat "rollback rehearsed" as meaning the four-step cycle was actually executed on the rig, with output captured, for every migration in the train — not that the rollback SQL was read and judged plausible. This is more expensive than a read-through but is the only version of "rehearsed" that catches a broken rollback before a real incident needs it. **Owner:** RTE, DBA (for migrations with cross-function grant complexity like 0364/0377).

## 10. Human/process — the soak spans days and sessions, context gets lost, nobody watches at 3am

**Mechanism:** a 72-hour soak necessarily spans multiple work sessions, likely multiple different Claude sessions and possibly multiple humans checking in. `memory/feedback_soak_clock_is_worker_uptime.md` names the core risk directly: "probe loops die on restart; durable signal is Cloud Run uptime; relaunch per session; verify uptime≥tier" — meaning a session that starts, checks the soak, and ends does not itself keep the soak "watched" in any continuous sense; the next session has to actively re-derive state rather than trust a carried-forward narrative. `memory/feedback_frozen_soak_head_not_orphan.md` names the mirror-image risk: a later session, unfamiliar with why a service is sitting on a non-tip SHA, might mistake an in-flight soak for an abandoned one and touch it.

Compounding this, this specific wave has an unusually high number of moving reference documents (the RC manifest, the choreography doc, the runbook, the release plan) that must all stay mutually consistent across sessions — `covered_main_shas` needs updating after every Mergify batch (choreography doc §2), the manifest's `included_prs[]` needs to reflect reality at freeze time and not drift, and `soak_mode`/`approval_status` on the manifest have strict, easy-to-invert semantics (approval_status must stay literally `"pending"` while `soak_mode` is set — flipping it early is itself a gate error).

The continuous monitors (§0.7) are specified as needing to "alert the operator in near-real-time... not 'check it at the next daily pass'" — but the runbook itself flags that the Sentry-based monitor is conditional on wiring that "may not land" (§7 above), meaning the actual paging mechanism for at least one monitor class may not exist for real, leaving log-grepping by a human as the fallback, which does not happen at 3am if nobody is watching.

**Earliest observable signal:** a gate checkpoint (T+24h, T+48h) where the operator cannot answer, with an artifact, what happened in the preceding window — no exception-register entries despite the window including a scheduler failure or a 5xx spike that should have triggered one; or a manifest whose `covered_main_shas` is stale relative to `main`'s actual tip, discovered only when a PR's gate check fails against it.

**Mitigation:** this is the hardest failure mode to fully close with process alone, and the source documents are honest that some pieces of it (real-time paging) depend on infrastructure (Sentry wiring) that may not be ready in time. The concrete, available mitigations: (1) every session that touches this soak re-reads the current state of the manifest, the runbook's gate checklist, and `gh variable list` before doing anything, rather than trusting a prior session's narrative summary (this is already the standing `CLAUDE.md` §1.11A bootstrap requirement — the soak just makes the cost of skipping it higher); (2) the daily observation checklist (§0.7) is run as a literal command sequence, with output captured to files, at minimum three times across the 72h window as already specified, and a named person/session is responsible for each of those three checkpoints in advance rather than "whoever happens to be online"; (3) build the log-pattern monitor from §7 above as a polling script with a webhook rather than depending solely on Sentry wiring landing in time, since it's explicitly named as uncertain. **Owner:** RTE (owns session-to-session continuity and the polling-script fallback), Carson (the one human constant across sessions — final sanity check that the soak's story is internally consistent at each gate, not just that boxes are checked).

## What must be true for this soak to be worth running — go/no-go checklist

This is the honest bar. If any row is false when the clock is proposed to start (or at any gate checkpoint thereafter), the soak is not producing merge-grade evidence at that moment, regardless of elapsed time.

- [ ] **T+0–2h smoke gate fully green**, including a real end-to-end SECURED anchor on signet and all 5 Cloud Scheduler jobs confirmed firing — not "provisioning succeeded."
- [ ] **`ENABLE_ORG_CREDIT_ENFORCEMENT=ON` and `ENABLE_OUTBOUND_WEBHOOKS=ON` verified live on the rig** (not assumed from the manifest) at clock start and re-checked at every gate.
- [ ] **`vars.DEPLOY_WORKER_PAUSED=true` on the live GitHub repo, re-checked at every gate**, not just confirmed once before Wave M's first merge.
- [ ] **The rig's image digest matches the frozen head at every gate checkpoint** — any mismatch is a clock reset, not a note.
- [ ] **`staging-honesty-preflight.ts` reports `clean_mirror` at provisioning AND after every migration applied to the rig thereafter.**
- [ ] **Every §5 named exercise (not generic load) produces its own artifact**, tied explicitly to the changed surface it validates: mixed-format bulk ≥100, 22-format matrix, SCRUM-3031 repeat-submission timing, RPC-revoke both-halves, `x-org-id` isolation under concurrent load at T+24h/T+48h/T+72h specifically.
- [ ] **The soak's own volume/concurrency numbers are reported honestly against the 10k-DAU A3–A5 targets**, including an explicit statement if it did not reach them — never silently substituted as 10k-DAU evidence.
- [ ] **A log-pattern monitor for the named fail-open strings (`"falling back to..."`, credit-deduction failure lines) is running independent of Sentry wiring status.**
- [ ] **All migration rollbacks in the train were actually executed (apply → rollback → confirm → re-apply → confirm idempotent) with captured output**, not read-and-judged-plausible.
- [ ] **The exception register exists and either has entries or has a credible, monitored basis for being empty** — an unmonitored empty register is not evidence of a clean run.
- [ ] **A named person owns each of the three (minimum) daily-checkpoint reviews in advance**, and every session touching the soak re-reads current manifest/gate/variable state before acting rather than trusting a carried-forward summary.
- [ ] **Gate G4 (deploy un-pause) has a named owner and is treated as its own closing step**, not implied by "the wave is soaked."
- [ ] **Manifest `approval_status` stays literally `"pending"` throughout, flipped to `"approved"` by Carson only at T+72h exit with every above box checked** — not flipped early as a convenience, not left `"pending"` after real maturity either.

If every box above is true at T+72h, the soak has produced evidence worth an auditor's or a launch decision's trust. If any is false, the honest answer is: not yet — extend, fix, or re-run the specific gate that failed, not the whole clock, unless the failure was a clock-reset event (§2, §8) in which case it is the whole clock.
