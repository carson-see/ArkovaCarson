# services/worker/scripts/load-test

k6 load-test profiles for SCRUM-1024 SCALE-02 (10K DAU target). Requires `k6` installed (`brew install k6`).

## Files

- `baseline.js` — Current production traffic mix (~5 rps, 60s). Establishes a baseline before scaling tests.
- `10k-dau.js` — 10K DAU-equivalent: 100 rps sustained + 500 rps burst, 5 min. p99 < 500ms, zero 5xx.
- `backpressure.js` — Sustained webhook ingestion at 200 rps, 90s. Verifies 503 + Retry-After when queue exceeds 10K pending, and clean recovery after drain.
- `docusign-volume.js` — DocuSign Connect volume profile (SCRUM-2094): 100 rps, 30 min, 15% signed-webhook mix. DocuSign-leg p99 < 300ms, err < 0.1%. Refuses to start without `DOCUSIGN_HMAC_KEY`.
- `lib/docusign-synth.js` — Pure, runtime-agnostic synthetic Connect-payload generator (mix selection + `envelope-completed` payload + canonical serialization). Imported by BOTH the k6 harness and Vitest. No crypto/clock/RNG — caller supplies ids/timestamps so output is byte-deterministic. **2026-08-30 (docusign-bilateral-2026-08, CTO Decision Record R9):** extended with the bilateral soak generators — see the dated entry below.
- `lib/docusign-synth.test.ts` — Vitest cross-validation: synthetic payloads are accepted by the REAL receiver (`parseDocusignConnectPayload`, `verifyDocusignConnectHmacMultiKey`, `extractNotaryData`). Guards against the generator drifting from the webhook schema.
- `lib/k6-docusign.js` — k6-only glue (imports `k6/http` + `k6/crypto`): signs `lib/docusign-synth.js` output and assembles the HMAC-signed POST. Not unit-tested for the ORIGINAL `executeScenario` path (k6-only; covered indirectly via the Vitest payload+HMAC contract) — the NEW bilateral glue below (`executeBilateralStep`/`executeBilateralRequest`) IS unit-tested (k6/http + k6/crypto + k6 `sleep` mocked) since its `signAs`/query-marker/delay dispatch logic is easy to get wrong silently.
- `lib/docusign-bilateral-synth.test.ts` — **2026-08-30 (docusign-bilateral-2026-08, R9):** cross-validates the bilateral generators. Real cross-validation (against `parseDocusignConnectPayload` / `verifyDocusignConnectHmacMultiKey`, unchanged, already-merged code) for the wire-shape and HMAC contract; a clearly-labeled PINNED CONTRACT (transcribed from `gh pr diff 2474`/`2476`, NOT an import) for `DocusignCapturedSigner`'s GUID-shape/cap and `classifyDirection`'s decision rule, since PRs #2472/#2474/#2476 are all open/unmerged as of this writing — swap each pinned block for a real import the moment its PR merges (each block says exactly what to swap and how to detect the moment to do it).
- `docusign-bilateral-soak.js` — **2026-08-30 (R9):** k6 driver for the bilateral soak. Fires the `BILATERAL_MIX` family set (15 named families: 3 outbound/R6 variants, 2 inbound/R4 variants, 6 adversarial/security families including `self_forgery` and `self_forgery_provenance_conflict` (F1), 4 malformed/ingress-robustness families) at a configurable steady RPS across two synthetic orgs (`DOCUSIGN_ORG_A_*` / `DOCUSIGN_ORG_B_*`), for a configurable duration — designed for the T3 48h continuous soak window. Thresholds on "response matched its family's documented `expectStatus`", NOT on a blanket zero-errors bar (401/413/200-duplicate are EXPECTED outcomes for the adversarial/malformed families). Refuses to start without both orgs' distinct account_id+key pairs and the shared fallback key.
- `docusign-guard-probe.js` — **2026-08-30 (R9, targets PR #2472):** standalone Node script (NOT k6 — a direct Supabase-client probe, not a webhook POST). Authenticates as a REGULAR user (never service_role — asserted structurally, `docusign-guard-probe.test.ts` greps the source for any `SERVICE_ROLE`-shaped token) and attempts to write forged `connector_source`/`account_id`/`_signers` keys directly into an owned anchor's `metadata`, to prove the PR #2472 write-authority guard (migration ~0423, unmerged — verify numbering with `gh pr view 2472` before citing it) strips/rejects them. Uses a distinctive sentinel (`GUARD_PROBE_SENTINEL`) the companion evidence SQL independently greps the whole `anchors`/`connector_artifact` tables for.
- `docusign-guard-probe.test.ts` — unit tests for the probe's own decision logic (`assessGuardResult`) and Supabase call shape (`attemptForgedMetadataWrite`, against a minimal mock client — there is no real guard to exercise pre-merge).
- `docusign-bilateral-evidence.sql` — **2026-08-30 (R9):** SOC2 T3 soak evidence queries, parameterized via psql `\set`/`-v` (`org_a_account_id`, `org_b_account_id`). Seven sections: (1) outbound `_signers` capture + PII/cap checks, (2) inbound DECLARED_UNVERIFIED anchor counts, (3) F1 provenance-conflict alert counts (`job_queue.last_error ILIKE '%docusign_connector_artifact_provenance_conflict%'`) + the actual forbidden-outcome query (an outbound job reaching `status=completed` for an envelope an inbound row already owns), (4) guard-probe sentinel leak check (whole-table, independent of the probe run), (5) nonce replay integrity (DB-side cross-check only — the authoritative replay count is the k6 run's own summary), (6) per-org isolation (connector_artifact/nonce rows never cross-attributed between the two synthetic orgs), (7) worker-uptime continuity PROXY (explicitly NOT the authoritative signal — see `memory/feedback_soak_clock_is_worker_uptime.md`; cite Cloud Run revision uptime instead). `connector_source`/`_direction`/`_signers` are `metadata` jsonb keys, NOT real columns; `fingerprint_source` IS a real `anchors` column (migration 0376/0384); `job_queue` has no `org_id` column (goes through `payload->>'org_id'`) — see the file's own schema-note header.
- `README.md` — Target profiles, running instructions, threshold definitions, DocuSign env vars.

## Constraints

- Set `WORKER_URL` env to target (local / staging / prod).
- Never run `10k-dau`, `backpressure`, `docusign-volume`, or `docusign-bilateral-soak` against prod outside a coordinated maintenance window.
- `docusign-volume.js` and `docusign-bilateral-soak.js` POST real signed envelopes through the full ingestion path — run them **only against an isolated staging rig** (CLAUDE.md §1.11/§1.11A). `docusign-bilateral-soak.js` additionally needs the rig seeded with TWO DocuSign integrations (org A + org B, each with its own `hmac_keys` entry) — a single-integration rig cannot exercise the `inbound_declared_hash` family as a true cross-org path or the per-org-isolation evidence query. Never shared staging mid-soak.
- The DocuSign leg degrades to `/health` when `DOCUSIGN_HMAC_KEY` is unset, so a default `10k-dau` run never POSTs unsigned webhook traffic. (The old `loadTestGuard.ts` drop-middleware never shipped — see README "Notes".)
- `lib/docusign-synth.js` must stay dependency-free ESM so both runtimes import it. If you change the payload shape, the Vitest suite must still pass against the real receiver.
- **PR-state caveat (as of 2026-08-30):** the bilateral harness above (`docusign-bilateral-soak.js`, `docusign-bilateral-evidence.sql`, `docusign-guard-probe.js`, `lib/docusign-bilateral-synth.test.ts`) was built while PRs #2472/#2474/#2476 were ALL open and unmerged — it is tooling-only (T0) and does not run against any live rig yet.
