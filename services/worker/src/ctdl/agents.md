# services/worker/src/ctdl/agents.md

CTDL/CE Registry serialization helpers for public credential representations.

## 2026-06-11 CTDL PII Safety + Real CTIDs (PR #1146)

- `ctdl-serializer.ts` runs value-level PII checks before emitting public JSON-LD. High-confidence PII in free-text fields (email, phone, SSN-like values) is suppressed via `cleanPublicFreeText`; transcript-like education records (`DEGREE`/`CERTIFICATE` + transcript/record signal) whose free text still trips the learner-name heuristic fail closed via `CtdlPiiSafetyError` (route returns 404, audit outcome `safety_blocked`). This PII gate is *additive* to — and does not change — main's public CTDL contract.
- Do not fabricate Credential Engine CTIDs from Arkova public IDs. Emit `ceterms:ctid` only when a real CE CTID is provided explicitly on the credential/issuer object (shipped via #1178).

## 2026-06-24 No-fake-CTID guard (SCRUM-2373 / CE-02)

- `ctdl-ctid-guard.ts` is the single source of truth for "is this a real CE CTID" (`ce-` + v4 UUID, `REAL_CTID_PATTERN`). The serializer no longer *silently drops* a non-matching CTID — it now **fails closed**: `assertRealCtidOrAbsent(value, 'credential'|'issuer')` returns the real CTID, returns `undefined` for an honest absence (field omitted), or **throws `FabricatedCtidError`** for a fabricated value (`ce-<arkova-id>`, `urn:ctid:...`, `ce-xxxx`, empty). A belt-and-suspenders `assertNoFabricatedCtidInJsonLd(body)` scans the assembled body before validation.
- Error messages are value-free (never echo the offending CTID). In the HTTP path a thrown `FabricatedCtidError` hits the endpoint's generic catch → 500 `internal_error`, audit outcome `error` — never a published body, never a synthesized placeholder. No "listed in the Registry" copy is emitted (CLAUDE.md §1.13 R-7).
- When a real CTID source lands, populate `CtdlAnchor.ctid` / `issuer.ctid` from it; the guard already accepts real CTIDs. (Note: `normalizeAnchorRow` in `credentials-ctdl.ts` does not yet select a CTID column, so live output omits CTIDs today — honest, not fabricated.)

## Files
- `ctdl-type-map.ts` - maps every Arkova `credential_type` enum value to a CTDL JSON-LD `@type`.
- `ctdl-serializer.ts` - builds public-safe CTDL JSON-LD from already-anchored credential records.

## Rules
- Keep CTDL output public-safe: never emit internal UUIDs, fingerprints, user IDs, recipient emails, raw metadata, or source filenames.
- Serializer changes must keep required CTDL fields covered by tests: `@context`, `@type`, `ceterms:name`, `ceterms:offeredBy`, `ceterms:credentialStatusType`, `ceterms:dateEffective`, and `ceterms:verificationServiceProfile`. `ceterms:ctid` is optional and must only be emitted when a real Credential Engine CTID is provided explicitly.
- If `credential_type` enum values change, update `CTDL_TYPE_MAP` and the coverage test in the same PR.

## 2026-06-24 expirationDate gated by status (SCRUM-2374 / CE-03 — status layer, PR #1305)

- `ceterms:expirationDate` is emitted ONLY for term-bound statuses — `statusAllowsExpiration(status)` in `ctdl-type-map.ts` returns true for `ACTIVE`/`SECURED`/`EXPIRED` and false for `REVOKED`/`SUPERSEDED` (and all non-publishable statuses). A REVOKED or SUPERSEDED credential ended for an unrelated reason, so a forward-looking expiry would contradict the status.
- `statusAllowsExpiration` is the single source of truth, shared by the serializer (gates emission, Arkova-status layer) and `ctdl-validation.ts` (cross-field invariant at the CTDL-status layer: a body with `ceterms:expirationDate` AND `ceterms:credentialStatusType ∈ {ceterms:Revoked, ceterms:Superseded}` is rejected). The validator is the independent second check for any future code path that re-introduces the conflict.

## 2026-07-01 expiration SEMANTICS — person vs offering (SCRUM-2374 / CE-03, S2)

- Builds on the status-layer gate above. Per Jeanne Kitchens (Credential Engine, SCRUM-2294): CTDL `ceterms:expirationDate` is the **RESOURCE-AVAILABILITY / offering** expiry — the date the credential resource (the program/offering) is no longer offered — NOT the expiry of a credential issued to a **person**.
- Two distinct fields on `CtdlAnchor`:
  - `expiresAt` (ISSUED-PERSON expiry, from `anchors.expires_at`) is read but **NEVER** routed to `ceterms:expirationDate`. Person-level validity belongs to the OB3/W3C VC issued-credential layer (SCRUM-2296), not class-level CTDL. Emitting it is the exact conflation Jeanne flagged.
  - `resourceAvailableUntil` (offering expiry) is the ONLY source for `ceterms:expirationDate`, still status-gated via `statusAllowsExpiration`. Derived in `normalizeAnchorRow` (`credentials-ctdl.ts`) from an allow-listed metadata key set (`resource_available_until`, `offering_available_until`, `offering_end_date`, + camelCase). Non-date values are ignored (honest omission). Arkova anchors issued artifacts, not offering catalogs, so this is absent for almost all live anchors → `ceterms:expirationDate` is honestly omitted by default.
- R-7 safe: it only *narrows* what the public body asserts; no new external claim, no CTID behavior change.

## 2026-07-06 ContactHour credit via ValueProfile (SCRUM-2375 / CE-04, S3)

- CE continuing-education credit is emitted as `ceterms:creditValue` → an array of ONE `ceterms:ValueProfile` with `schema:value` (positive finite number) + `ceterms:creditUnitType` → `CredentialAlignmentObject` targeting `creditUnit:ContactHour` (framework `https://credreg.net/ctdl/terms/creditUnit`). Per Jeanne Kitchens' CTDL correction: NEVER a bare scalar. Plain strings (not language maps) for frameworkName/targetNodeName, matching the module's other `ceterms:name`-style fields.
- Source: allow-listed anchor metadata keys only (`contact_hours`/`credit_hours`/`ce_credit_hours` + camelCase) via `contactHoursFromMetadata` in `credentials-ctdl.ts`; `normalizeContactHours` (exported by the serializer — single plausibility gate, 0 < v ≤ `MAX_CONTACT_HOURS` = 1000, the constant now defined in and exported from `ctdl-validation.ts` so validator and serializer share ONE ceiling) is shared by the row layer and emission layer. Absent/zero/negative/non-finite credit → the property is OMITTED (honest omission, never a 0-hour profile).
- Emission is restricted to continuing-education types (`CPE`/`CLE` — `isContinuingEducationCreditType` in `ctdl-type-map.ts`); a contact-hour value on any other type is ambiguous and omitted. `ctdl-validation.ts` `validateCreditValue` is the independent second check (rejects bare scalars, non-positive values, values above `MAX_CONTACT_HOURS`, arrays with ≠ 1 ValueProfile, non-ContactHour units). Export-only — NO persisted mapping table (PO default).
- **CONFLATION GUARD:** the CE ContactHour credit has NOTHING to do with the billing `credit_ledger` (paid anchoring credits). `ctdl-credit-conflation-guard.test.ts` scans the CTDL production sources (comment-stripped) and fails on any credit_ledger/billing reference or `/billing/` import.

## 2026-07-01 offering-expiry PII/ISO hardening (PR #1378, S2 fix-team)

- **Root cause (MED PII-leak + LOW non-ISO):** `resourceAvailableUntilFromMetadata` (`credentials-ctdl.ts`) returned an allow-listed metadata value *verbatim* after only a lenient `Date.parse()` gate. `Date.parse("recipient@example.com 2030-01-01")` is valid → the issuer email leaked into `ceterms:expirationDate` on the public projection; non-ISO strings like `"12/31/2030"` also passed through verbatim.
- **Fix:** `canonicalizeResourceAvailableUntil` now (1) rejects any value carrying high-confidence PII via the shared `containsHighConfidencePii` (email/phone/SSN — now exported from `ctdl-serializer.ts`) and (2) canonicalizes to a bare ISO string via `new Date(value).toISOString()`. Only a canonical date can ever reach `ceterms:expirationDate`; anything else is omitted (honest omission).
- **Validator tightened:** `isIsoDateLike` in `ctdl-validation.ts` is now a real ISO-8601 check (`YYYY-MM-DD` or full date-time with optional offset + real-instant validity) instead of raw `Date.parse()`. This is the independent second check for `ceterms:expirationDate` / `dateEffective` / `revocationDate`; a locale or PII-prefixed string can no longer validate. Note: all DB-sourced dates fed to these fields are `timestamptz` full-ISO, so this narrowing does not affect legitimate values.

## 2026-08-01 outbound value-level PII scrub gate (SCRUM-2293 / 2299 / 2300)

- **Live prod leak, verified before the fix** (prod `git_sha 8e6a804e2`, `GET https://api.arkova.ai/v1/credentials/<id>/ctdl`): a `credential_type = 'TRANSCRIPT'` anchor served a person's full name in `ceterms:name` AND `ceterms:description` on the PUBLIC, UNAUTHENTICATED projection. Two holes: `isTranscriptLikeEducation` keyed on `DEGREE`/`CERTIFICATE` only (so `TRANSCRIPT` — the most PII-dense type we carry — was never gated), and it additionally required a literal transcript/record KEYWORD in the free text.

### The design decision, and why the obvious approach was rejected

**You cannot reliably detect a bare personal name in free text with regex, and attempting it is actively harmful.** The first implementation tried exactly that — "a capitalised pair is a person when introduced by a relational trigger (`for`/`to`/`by`/`with`) and not vetoed by an institutional word list." Measured against real inputs, it failed in BOTH directions simultaneously:

- It **404'd 28 of 32 real institution names** ("Issued by Johns Hopkins", "Issued by Red Hat", "Issued by Carnegie Mellon") and **13 of 18 ordinary credential titles** ("Introduction to Machine Learning"). A finite word list cannot veto an open class (proper nouns) — that is structural, not a tuning problem.
- It **still missed** the common leak shapes: a bare name as the entire field ("Jane Doe"), record-noun-first order ("Transcript: Jane Doe"), all-caps ("MARIA GONZALEZ"), and every non-ASCII name ("José García"), because `[A-Z][a-z]+` cannot express them.
- It was also **O(n²)** on unbounded issuer text (61 s on a 192 KB description) on a public unauthenticated endpoint.

So the shipped design does **not** look for names. For ACADEMIC-RECORD types it takes the decision SCRUM-2293's own AC states ("if NER unavailable/low-confidence, SUPPRESS THE FIELD rather than emit it"): **an academic record emits NO issuer- or extraction-authored free text.** `ceterms:name` comes from controlled vocabulary (`academicRecordName`, derived from the resolved CTDL `@type`); `ceterms:description` and `ceterms:revocationReason` are omitted. That is precision-independent — no heuristic decides whether a real credential publishes, no name shape can leak, and no legitimate credential goes offline.

**If you are tempted to reintroduce a name heuristic as a gate: don't.** The adversarial fixtures encode the shapes that defeat detection (all-caps, non-ASCII, apostrophes, hyphens, bare, mid-string) and the institution names a heuristic wrongly blocks. Both halves fail if the structural rule is replaced.

### What IS detector-based

- **`ACADEMIC_RECORD_LABELS` / `academicRecordName` live in `ctdl-type-map.ts`, beside `CTDL_TYPE_MAP`** — a DECLARED map, not a derivation. A camelCase-splitting derivation was tried and rejected: it produced "Master Degree" / "Bachelor Degree" (not idiomatic English on a partner-facing, CE-Registry-bound label), rendered a subType-less `DEGREE` as bare "Degree", and could not split consecutive capitals (`CQMCredential`). The whole argument for this name is that it is controlled vocabulary — so it is declared, with an honest `'Academic Credential'` fallback for an unmapped future type. Adding a credential type or degree level and forgetting its label is now a same-file omission.
- **`recordFreeText` in `buildCtdlJsonLd` is the CHOKE POINT.** "An academic record emits no issuer free text" is a property of the whole BODY, so it is enforced as one gate, not per-field ternaries. Route every future RECORD-DESCRIPTIVE field (a keyword, a subject, an alternate name) through `recordFreeText`, never `cleanPublicFreeText` directly — the body scan runs only high-confidence detectors and by this module's own premise cannot see a bare personal name, so forgetting the gate would be a SILENT regression of exactly the prod leak this closed. Issuer IDENTITY (`issuerName`, `subjectWebpage`) is deliberately not record-descriptive and stays emitted.
- **Why the detectors are NOT sourced from `utils/pii-scrub.ts`** (which calls itself the one source of truth for email/SSN/phone): that module exists for REDACTION in logs and Sentry, where over-broad patterns are free — they just mask more. This gate FAILS CLOSED on a public endpoint, where an over-broad pattern takes a real credential offline. Its SSN pattern is dash-only, its phone pattern matches almost any digit run, and its fingerprint/UUID patterns would fire on our own public identifiers. Different cost function, deliberately different patterns. Do not merge them.
- `ctdl-pii-guard.ts` is the single source of truth. `CtdlPiiSafetyError` moved here and is re-exported from `ctdl-serializer.ts`, so route `instanceof` checks and import sites are unchanged. Keep the module dependency-free — any future Registry publish path must import it without dragging in the serializer.
- `containsHighConfidencePii` covers only what regex is actually good at: FORMAT- and KEYWORD-anchored values — email, US phone, **international phone** (candidate regex + digit-count check in code, so "+44 20 7946 0958" matches while "+1 2026-03-27" does not), SSN, and SCRUM-2299's two named gaps: keyword-anchored **date of birth** and **student/learner/enrollment ID** (≥4 digits, so `PHIL 2020` cannot trip it). Runs for EVERY credential type.
- **SSN requires real separators, or its keyword.** The old optional-separator form matched any bounded 9-digit run — a campaign id or a numeric path segment in an issuer URL — which on a fail-closed gate 404s every credential that org owns.
- **Every separator is a bounded class (`[\s:#-]{0,4}`), never `\s*X?\s*`**, which enumerates O(n²) splits of a whitespace run before failing. Plus `MAX_SCAN_CHARS` (4000) bounds every scan: detectors run on RAW DB text at some call sites (e.g. `canonicalizeResourceAvailableUntil`), on a public endpoint, on a single-threaded runtime.
- `containsLearnerNamePii` keeps the two pre-existing narrow patterns VERBATIM, used ONLY for field suppression on non-academic types (an honest omission) — **never as a gate**. Do not widen them, and never add bare prepositions as triggers.
- `assertNoPiiInJsonLd(body)` is the assembled-body backstop for values that never route through `cleanPublicFreeText`. **High-confidence detectors only** — the name heuristics deliberately do not run here, because this scan fails CLOSED for every type and a heuristic false positive would take a legitimate credential offline. Depth budget fails closed, mirroring CE-02/CE-06a.
- `ceterms:subjectWebpage` now drops its **userinfo, query string, and fragment** (`stripUrlQueryAndFragment`, string-in/string-out — it does not mutate a caller's `URL`). Structural, not heuristic: those three are where an identifier or bearer material rides into an otherwise innocuous field, and an issuer's public homepage needs none of them. `lib/credential-evidence.ts` `normalizeCredentialSourceUrl` does a related but DIFFERENT job — it PRESERVES non-tracking query params so an evidence URL still resolves to the exact document — so the two are deliberately not merged.
- **`normalizePublicText` is the one text-shape definition** for this surface (strip control chars, collapse whitespace, trim, bound length); `cleanPublicString` in the serializer delegates to it, so the two hand-rolled copies that already disagreed about ordering are gone. It uses a regex rather than `Array.from().filter().join()` — measured 15-20x faster for byte-identical output, which matters on a public unauthenticated endpoint. `containsOutboundFreeTextPii` is the single field-suppression predicate, so a caller cannot forget half the check and the value is normalized once rather than once per detector family.

- Fixtures: `ctdl-pii-guard.adversarial.test.ts` runs each case through the REAL serializer asserting "scrubbed OR fail-closed, never emitted", plus precision blocks pinning that institution names, ordinary titles, and numeric issuer URLs still publish, plus a serialization-time budget.
