# scripts/ops/agents.md

Operational scripts for database maintenance and production infrastructure.

## Files
- **`ensure-pipeline-dashboard-cache-cron.ts`** — ensures the `refresh-pipeline-dashboard-cache` pg_cron job exists with correct schedule (`*/2 * * * *`), support index, and stats function. Builds read-only evidence SQL for auditing.
- **`ensure-pipeline-dashboard-cache-cron.test.ts`** — colocated tests for the cron management script.
- **`webhook-delivery-health.sql` (WH-7, SCRUM-2899)** — read-only verification query for the webhook-delivery fix. Reports `webhook_delivery_logs` status buckets + `webhook_dead_letter_queue` counts by `failure_kind` per week, plus a single-number gauge (unresolved `log_write` DLQ rows in the last 7 days ≈ 0 when healthy). Run against prod before/after the flag flip to confirm the "fetch failed" silent-drop class is gone.
- **`materializer-preflight.ts` (SCRUM-2984, SCRUM-2917 prod-EXECUTE prereq)** — read-only preflight for the proof-materializer prod backfill (~2.96M-row `anchor_proofs` insert campaign). Reports the anchors-vs-proofs row gap (`pg_class.reltuples` planner estimate vs exact `anchor_proofs` count — never an exact `count(*)` on the hot `anchors` table, per R0-8/SCRUM-1254), table bloat (`pgstattuple_approx` when the extension is installed, else `pg_stat_user_tables` dead-tuple ratio), autovacuum staleness, and lock contention on `anchors`/`anchor_proofs` (flags the known SCRUM-3031 `batch_insert_anchors` wedge signature by name, gated on a `WEDGE_SIGNATURE_DURATION_FLOOR_SECONDS` (5s) duration floor so PR #1730's fixed, fast reuse of that RPC name doesn't spuriously WARN). Emits a `PASS`/`WARN` verdict per the thresholds defined in `docs/runbooks/ops/proof-materializer-execute.md` §2 and exits non-zero on `WARN` or any connectivity failure. Connects via the Supabase Management API's `/database/query/read-only` endpoint (project ref + access token via env/flags — never a raw Postgres connection string or an embedded credential), the same mechanism `scripts/ci/staging-honesty-preflight.ts` uses — deliberately not a new `pg` driver dependency. Never mutates; never invokes the materializer job itself.
- **`materializer-preflight.test.ts`** — colocated tests for the mapping/verdict logic, exercised against mocked query-result rows (no real Supabase call except a stubbed-`fetch` test of `queryReadOnly` itself).
- **`mfa-break-glass.ts` (SCRUM-3584)** — service-role-only tool to remove a lost MFA factor for a locked-out user (no in-app self-service path exists by design — GoTrue requires aal2 to unenroll a VERIFIED factor, and nothing lets a user without their device reach aal2). Implements the BINDING safety sequence from the MFA-enforcement CTO plan: resolve user by email — fast path via an indexed `profiles.email` lookup confirmed with `auth.admin.getUserById`, falling back to a paginated `auth.admin.listUsers` scan (terminated by `nextPage` going null, not a short-page heuristic — a full-but-final page is real) only when profiles has no row or the fast path is inconclusive — → list + print every factor → validate `--factor-id`/`--all` against that user's actual factors → write an `audit_events` `MFA_BREAK_GLASS_REQUESTED` (`event_category='SECURITY'`) row **before** any delete → `auth.admin.mfa.deleteFactor` per selected factor → write an `audit_events` `MFA_BREAK_GLASS_COMPLETED` row recording per-factor outcome. The fast-path lookup queries `.eq('email', email.trim().toLowerCase())` — the SAME transformation (no NFKC) as the DB trigger that populates `profiles.email`, so it matches exactly what got persisted (same precedent as `services/worker/src/api/invitations.ts`'s own profiles-by-email lookup; an earlier version of this tool queried the NFKC-normalized form instead and silently missed rows whose NFKC form diverges from plain trim+lowercase, e.g. fullwidth/ligature characters — reverted, since any such miss still resolves correctly via the `listUsers` scan below, which normalizes fully). The fast path also folds `org_id` into that same SELECT (`select('id,email,org_id')`), so a fast-path hit costs exactly one profiles query — `lookupOrgId` runs separately only when resolution instead came from the `listUsers` scan, which can't return `org_id`. Either way, the value returned as `user.email` (and compared against `CONFIRM_MFA_BREAK_GLASS`) is always the LIVE `auth.admin.getUserById` email, never the profiles row used to find it — a stale/divergent `profiles.email` only affects which row is matched, not what the tool trusts afterward. Audit `details` are ordered with identifying fields (`user_id`, `factor_ids`, `statuses`, `ticket`, `operator`, `host`) BEFORE the free-text `friendly_names`/`reason`, and are truncated structurally (via `services/worker/src/utils/utf16-truncate.ts`'s `truncateUtf16Safe`, re-stringified — never a raw slice of the serialized JSON) if the 10000-char `audit_events.details` CHECK would otherwise be exceeded. Dry run (no `--apply`) is the default and writes nothing; the prod-host hard-deny applies to dry runs too, not just apply. `--apply` additionally requires `CONFIRM_MFA_BREAK_GLASS=<resolved email>` (case-insensitive, NFKC-normalized) and, for `--all` specifically, a SECOND ack `CONFIRM_MFA_BREAK_GLASS_ALL=<resolved email>` (same two-tier shape as `provision-isolated-rig.sh`'s `CONFIRM_REAL_CONFIG`) — and, against a prod-ref `SUPABASE_URL`, `ALLOW_PROD_BREAK_GLASS=1` (checked in `main()` before the service-role client is even constructed; `runBreakGlass()` re-checks it too as defence in depth). CLI parsing declares every option `multiple: true` in one node:util `parseArgs` call: `parseArgs` itself rejects a flag whose value token looks like another flag (e.g. `--reason --ticket ...`, naming `--reason` as the culprit) before any duplicate check runs, and a genuinely repeated flag (e.g. two `--email` values, or `--all`/`--apply` given twice) shows up as an array of length > 1 in `parseArgs`'s own result — no separate `findDuplicateFlags` pre-scan exists any more (removed in the SCRUM-3584 simplify pass; a duplicate-scan-BEFORE-parseArgs ordering used to misdiagnose the swallowed-value case as a repeated LATER flag instead of the real missing-argument error). `--ticket` accepts only `SCRUM-NNNN` or the exact Jira browse URL — not an arbitrary URL. `isDirectEntrypoint`'s `realpathSync` comparison falls back to comparing the unresolved path strings (and writes one stderr line saying so) if `realpathSync` itself fails, rather than silently treating any realpath failure as "not the entrypoint" (which used to risk `main()` never running — exit 0, no output). Never logs `SUPABASE_SERVICE_ROLE_KEY`. Full procedure: `docs/runbooks/mfa-break-glass.md`. Exit codes: `0` success, `1` validation/precondition (nothing written), `2` intent-audit insert failed (aborted before any delete), `3` completion-audit insert failed after delete(s) attempted (prints the row to insert manually — loudest failure mode), `4` completion audit recorded but one or more per-factor deletes failed. **Soak tier: T2**, not the path-detector's T1 default — `scripts/ops/` isn't in the detector's auth/security-sensitive exclusion list, but CLAUDE.md §1.12 excludes any "security-sensitive surface" from T1 regardless of path, and a tool that deletes a user's auth factor via service-role is exactly that; declare T2 in the PR body.
- **`mfa-break-glass.test.ts`** — hand-rolled fake `SupabaseAdminLike` (no real Supabase project) covering: dry-run-writes-nothing (incl. the zero-factor `--all --apply` path, which is a real reachable "nothing to delete" case, not a logic bug); ## Conventions
- Scripts are idempotent and safe to re-run.
- Evidence queries return JSON for audit trail verification.
- Changes to cron schedules or indexes require staging soak (T2 minimum).
- Read-only preflight/reporting scripts (e.g. `materializer-preflight.ts`) reach Postgres only through the Supabase Management API's `/database/query/read-only` endpoint or existing RPCs — no raw `pg`/`postgres` driver dependency for one-off ops tooling; keeps DB access on the locked Supabase-only stack (CLAUDE.md §1.1).
